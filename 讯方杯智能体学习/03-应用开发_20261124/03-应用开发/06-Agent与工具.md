## 🎬 一、Agent 是什么

![[907-Agent与FunctionCalling.mp4]]

### 与普通对话的区别

| | 普通对话 | Agent |
|---|---|---|
| 输入 | 用户问题 | **用户目标** |
| 输出 | 文本回答 | **任务完成结果** |
| 过程 | 一问一答 | 调工具、读数、执行操作 |
| 类比 | **顾问**（只给建议） | **助理**（帮你做） |

**经典例子**：
> 「查一下明天北京天气，如果低于 10 度就在日程里加一条带厚外套的提醒」

- 普通对话：只能告诉你天气
- Agent：查 API → 判断温度 → 调日历 API → 加提醒，**全程不用你指挥**

### 四环节循环

```text
感知 Perceive → 规划 Plan → 行动 Act → 反馈 Reflect
                    ↑                        │
                    └────────────────────────┘
```

> 🎯 **「反馈」是 Agent 区别于普通对话的核心机制** —— 检查结果不符合预期就调整重来。

### 四个核心组件

| 组件 | 是什么 |
|---|---|
| **大脑（LLM）** | 理解任务、推理决策 |
| **手脚（Tools）** | 搜索引擎、计算器、代码执行器、数据库 |
| **经验（Memory）** | 短期（上下文）+ 长期（历史记录） |
| **思维（Prompt）** | 角色、工具规则、行为约束 |

### 三种类型

| 类型 | 说明 | 适合 |
|---|---|---|
| **单 Agent** | 独立完成所有任务 | **大部分场景** |
| **多 Agent** | 分工合作 | 复杂工作流 |
| **ReAct 型** | 推理+行动交替 | 需要多步思考 |

> 💡 **大部分场景用单 Agent 就够了**，多 Agent 是复杂情况才需要。

### 什么时候该用 Agent

| 适合 | 不适合 |
|---|---|
| 多步操作 | 纯文本生成（写文章、翻译） |
| 需要工具协调 | 简单知识问答 |
| 需要条件判断 | 一次对话能完成的 |

> 🎯 **判断标准**：**一次对话能完成 → 不用 Agent；需要多步操作 + 工具 + 判断 → 用 Agent。**

## 🔧 二、Function Calling：工具调用的底座

### 完整流程（五步）

```text
1. 开发者告诉模型有哪些函数可用（名称、参数、用途）
2. 用户提问
3. 模型判断需要调用 → 输出函数名和参数（JSON）
4. 系统执行函数，把结果返回给模型
5. 模型基于结果生成最终回答
```

### 代码实现要点

**第一步：用 JSON Schema 描述函数**

```python
tools=[{
    "type": "function",
    "function": {
        "name": "sum_number",
        "description": "计算一组数的和",       # ← 模型靠这个判断何时调用
        "parameters": {
            "type": "object",
            "properties": {
                "numbers": {"type": "array", "items": {"type": "number"}}
            }
        }
    }
}]
```

**第二步：模型返回 tool_calls**

```python
response = client.chat.completions.create(..., tools=tools)
if response.tool_calls is not None:
    tool_call = response.tool_calls[0]
    args = json.loads(tool_call.function.arguments)
    result = sum(args["numbers"])              # 本地执行
```

**第三步：把结果回传给模型**

```python
messages.append(response)                       # ← 必须！否则报错
messages.append({
    "tool_call_id": tool_call.id,               # 必须
    "role": "tool",                             # 必须
    "name": "sum_number",                       # 建议加
    "content": str(result)                      # 必须转成字符串
})
final = client.chat.completions.create(messages=messages)
```

> ⚠️ **两个必须**：
> 1. **`messages.append(response)` 不能漏** —— 模型的 tool_calls 必须先进入上下文，否则报错
> 2. **`tool_call_id` 和 `role` 是必须参数**，`content` 必须是字符串

> 💡 **`description` 字段极其重要** —— 它是模型判断"什么时候该用这个工具"的唯一依据。
> 写"计算一组数的和"比写"sum 函数"效果好得多。

## 🧠 三、Agent 的四个关键能力

### ① 常见工具类型

| 类型 | 例子 |
|---|---|
| 搜索 | Google / Bing API |
| 代码执行 | 跑 Python 做计算 |
| 数据库 | SQL 查询 |
| API 调用 | 天气、地图、支付 |
| 文件操作 | PDF 解析、Excel |
| 知识库检索 | RAG |

### ② 记忆管理

**问题**：上下文窗口有限，装不下所有历史。

| 策略 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **对话摘要** | 大幅压缩 token | 可能丢细节 | 长对话、客服 |
| **滑动窗口** | 实现简单 | 丢早期信息 | 通用对话 |
| **重要性评分** | 保留关键信息 | 需要额外判断 | 复杂场景 |
| **遗忘机制** | 像人脑衰减 | —— | 长期运行 |

### ③ 规划能力

**任务分解示例**：
```text
"写一份 DeepSeek-V3 技术分析报告"
  → 1. 搜索论文和官方博客
  → 2. 提取关键技术点（MoE、MLA、成本）
  → 3. 与 GPT-4、LLaMA-3 对比
  → 4. 整理成报告格式
```

> 规划能力**取决于模型的推理能力** —— GPT-4、DeepSeek-R1 分解得更好，小模型容易漏步骤。

### ④ 反思与纠错

```text
执行一步 → 检查是否符合预期
        → 不符合 → 分析原因（工具错了？参数不对？思路有误？）
        → 制定新计划 → 重新执行
```

> ⚠️ **必须设「最大迭代次数」** —— 否则可能无限循环（Dify 里可以配）。

## 🔄 四、ReAct 模式

**每一步三部分**：

```text
Thought（思考）— 分析当前状态，决定下一步
Action（行动）— 调用一个工具
Observation（观察）— 获取返回结果
```

**完整示例**：
```text
Thought: 我需要搜索 DeepSeek-V3 的技术参数
Action:  search("DeepSeek-V3 参数量 架构")
Observation: DeepSeek-V3 有 6710 亿参数，采用 MoE 架构...
Thought: 找到答案了，可以回复用户
```

> 💡 循环直到 Agent 认为任务完成。

## 🔌 五、MCP 协议

**问题**：每个 Agent 框架都有自己的工具接口格式，接一个新工具就要适配一遍。

**解答**：MCP（Model Context Protocol）由 Anthropic 提出，**统一工具接入标准**。

```text
类比：USB 统一了外设接口
```

**价值**：工具开发者**只实现一次**，所有支持 MCP 的框架都能用。

**已支持**：Dify、LangChain、Claude Desktop。

## 👥 六、多 Agent 协作

### 经典模式：研究员 + 写手 + 审核员

| 角色 | 职责 |
|---|---|
| **研究员** | 搜索信息、收集资料 |
| **写手** | 基于资料撰写内容 |
| **审核员** | 检查输出，指出错误，要求修改 |

> 三个 Agent 协作的效果**通常优于单个 Agent** —— 因为每个可以专注擅长的部分。

### 两个主流框架

| 框架 | 理念 | 适合 |
|---|---|---|
| **CrewAI** | **角色扮演**，组成 Crew 按流程协作 | 流程明确的场景 |
| **AutoGen** | **对话式协作**，支持人机协作 | 需要灵活协商的场景 |

## 🎛️ 七、Dify 平台开发 Agent

### 六步流程

```text
1. 创建「Agent」类型应用（不是「聊天助手」）
2. 选模型（推荐 DeepSeek-V3 或 GPT-4，推理要强）
3. 写系统提示词（角色 + 行为规则）
4. 加工具（内置搜索、代码执行、HTTP 请求等）
5. 配知识库（如需 RAG）
6. 测试调优
```

### 两个实用细节

**① 工具描述要写清楚**

```text
❌ "天气工具"
✅ "查询指定城市的当前天气和未来 3 天天气预报"
```

**② 知识库作为「工具」而非固定步骤**

> 在 Agent 的工具列表里加「知识库检索」，Agent **自己判断**要不要查。
> 比每次都检索更灵活，**减少不必要的开销**。

### 工作流节点类型

| 节点 | 作用 |
|---|---|
| LLM 节点 | 调用大模型生成 |
| 知识库检索 | 执行 RAG |
| 条件分支 | 按条件走不同路径 |
| 代码执行 | 跑 Python/JS |
| HTTP 请求 | 调外部 API |

**典型编排**：
```text
先检索 → 判断是否找到结果
        → 找到：生成回答
        → 未找到：调用搜索引擎
```

### 三类典型应用

| 应用 | 流程 |
|---|---|
| **智能客服** | 意图识别 → 调不同工具（查订单/工单/知识库）→ 回复 |
| **数据分析** | 读文件 → 写并执行 Python → 生成图表 → 写报告 |
| **编程助手** | 搜文档 → 写代码 → 执行测试 → 失败则自动修复 |

## ❓ 自测

1. Agent 和普通对话最本质的区别？
2. Function Calling 中，函数是在哪里执行的？
3. 为什么必须把 response 加进 messages？
4. 工具的 description 为什么重要？
5. MCP 解决了什么问题？

<details>
<summary>参考答案</summary>

1. 普通对话是"问题→回答"；Agent 是"目标→自主规划→调用工具→执行→反馈"的循环，能真的做事。
2. 在本地（你的代码里）执行，模型只负责输出函数名和参数，不执行任何代码。
3. 因为模型的 tool_calls 必须先进入对话上下文，后续的工具结果才能正确关联，否则 API 会报错。
4. 它是模型判断"什么时候该调用这个工具"的唯一依据，描述不清模型就不会用或用错。
5. 统一了 Agent 工具的接入标准，工具开发者只需实现一次，所有支持 MCP 的框架都能调用。
</details>
