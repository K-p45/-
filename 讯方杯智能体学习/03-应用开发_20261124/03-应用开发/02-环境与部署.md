## 🎬 一、Docker：为什么非用不可

![[902-Docker与昇腾部署.mp4]]

### 核心价值

> **一次构建，随处运行。**

**容器 vs 虚拟机**：

| | 虚拟机 | Docker 容器 |
|---|---|---|
| 内核 | **每个都带完整 OS** | **共享宿主机内核** |
| 启动 | 分钟级 | **秒级** |
| 体积 | 几个 GB | 几十 MB |
| 隔离性 | 完全隔离 | 进程级隔离 |

> 🎯 **"共享内核"是关键区别** —— 这是容器轻量的根本原因，也是考试常考点。

### 必会命令

| 目的 | 命令 |
|---|---|
| 查看版本 | `docker -v` / `docker-compose -v` |
| 拉镜像 | `docker pull nginx` |
| 运行容器 | `docker run -d -p 8080:80 nginx` |
| 查看运行中 | `docker ps` |
| 查看全部 | `docker ps -a` |
| 看日志 | `docker logs [容器ID]` |
| 停止 / 启动 / 重启 | `docker stop/start/restart` |
| **删除容器** | `docker rm [容器ID]` |
| **构建镜像** | `docker build -t myimage .` |
| 标记 / 推送 | `docker tag` / `docker push` |

**参数速记**：
```bash
docker run -d -p 8080:80 nginx
#          │  └─ 宿主机8080 → 容器80
#          └──── 后台运行
```

### 镜像 vs 容器

```text
镜像 = 只读模板（像 Class）
容器 = 运行实例（像 Object）
```

> 镜像由多层只读层组成，通过 Dockerfile 构建。容器可以启动、停止、删除。

### 国内镜像源（必配）

拉镜像慢是常态，必须配镜像加速。`daemon.json`：

```json
{
  "registry-mirrors": [
    "https://hub.rat.dev",
    "https://dockerpull.org",
    "https://mirror.azure.cn/"
  ]
}
```

> 💡 源经常会失效，多备几个，一个不行换下一个。

## 🎬 二、昇腾开发环境

### 单卡开发套件的五件套

| 组成 | 内容 |
|---|---|
| **硬件** | Atlas 300I（推理）/ 300T（训练）加速卡 |
| **操作系统** | openEuler（推荐）/ Ubuntu 18.04、20.04 |
| **驱动固件** | NPU 驱动，**版本必须与 CANN 严格匹配** |
| **CANN Toolkit** | 编译器、运行时、算子库 |
| **AI 框架** | **PyTorch + torch_npu**（最主流） |

### 安装三步

```bash
# 1. 确认识别到 NPU
lspci | grep Huawei

# 2. 装驱动 → 重启 → 验证
npu-smi info

# 3. 装 CANN Toolkit（.run 包，root 权限）
#    关键路径：/usr/local/Ascend/ascend-toolkit/
```

**环境变量**（写进 `~/.bashrc`）：
```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
```

这会自动设置 `LD_LIBRARY_PATH`、`PYTHONPATH`、`PATH`。

### PyTorch 适配

```bash
pip install torch==2.1.0 torch_npu==2.1.0
```

> ⚠️ **版本必须严格一致**，这是昇腾开发最常见的坑。

### 最常遇到的四个问题

| 问题 | 原因 | 解决 |
|---|---|---|
| `npu-smi` 找不到 | 驱动没装/环境变量没配 | 检查 `/usr/local/Ascend/`，重新 source |
| `import torch_npu` 报错 | torch 与 torch_npu 版本不匹配 | `pip list` 确认版本一致 |
| 加载模型 OOM | 参数超过 HBM 容量 | FP16/INT8 量化，或换小模型 |
| 推理异常慢 | 数据没放 NPU 上，频繁搬运 | 检查 `.npu()`，避免 fallback 到 CPU |

### NPU 监控要看什么

| 指标 | 正常范围 | 异常含义 |
|---|---|---|
| **AI Core 利用率** | 推理 30%-80% | 持续 <10% → 数据加载瓶颈 |
| **HBM 内存** | 模型加载后基本固定 | 接近 100% → 要换量化 |
| **温度** | 40-80°C | >85°C 触发降频 |
| **功耗** | —— | 评估运行成本 |

```bash
watch -n 1 npu-smi info
```

### 第一个 NPU 推理示例

```python
import torch
import torch_npu
from transformers import AutoTokenizer, AutoModelForCausalLM

model_path = 'deepseek-ai/DeepSeek-Coder-1.3B-Instruct'
tok = AutoTokenizer.from_pretrained(model_path)
model = AutoModelForCausalLM.from_pretrained(
    model_path, torch_dtype=torch.float16
).npu()                                  # ← 关键：放到 NPU
```

**观察到的现象**（很直观）：

| 阶段 | HBM | AI Core |
|---|---|---|
| 加载前 | ~0 MB | 0% |
| 加载中 | 逐步上升到 ~2.6 GB | —— |
| 推理中 | 略增（KV Cache） | 30%-80% 跳动 |
| 推理后 | 仍占用（模型还在显存） | 回到 0% |

**释放显存**：
```python
del model
torch.npu.empty_cache()
```

### 四条最佳实践

1. **用虚拟环境** —— conda 隔离依赖
2. **版本锁定** —— 把 CANN/驱动/torch/torch_npu 版本写进文档
3. **用 Docker** —— 华为官方 CANN 镜像作为基础
4. **养成监控习惯** —— 跑之前先 `npu-smi info` 看设备是否空闲

## 🚀 三、DeepSeek 轻量化部署

### 精度选择

| 精度 | 每参数 | 7B 模型显存 | 精度损失 |
|---|---|---|---|
| FP32 | 4 字节 | 28 GB | 无 |
| **FP16/BF16** | 2 字节 | **14 GB** | 几乎无 |
| **INT8** | 1 字节 | **7 GB** | 1-2% |
| **INT4** | 0.5 字节 | **3.5 GB** | 稍大但可接受 |

### vLLM：生产级推理框架

**核心创新：PagedAttention**

> 借鉴操作系统的虚拟内存分页思想，把 KV Cache 分成固定大小的「页」，按需动态分配。

**解决什么**：传统框架要为每个请求预分配大量 KV Cache，但实际大小差异大，导致**显存碎片化** —— 就像停车场有空位但都太小停不进去。

```text
传统：给每个请求预留一大块 → 浪费
vLLM：按页动态分配         → 利用率 95%+
```

**优势**：显存利用率提升 2-4 倍，支持连续批处理。

**启动服务**：
```bash
vllm serve deepseek-ai/DeepSeek-R1-Distill-Qwen-7B \
  --dtype float16 --max-model-len 4096 --port 8000
```

> 💡 **vLLM 兼容 OpenAI 接口**，所以调用方式和调 OpenAI API 完全一样。

### Docker 化部署四步

| 步骤 | 做什么 |
|---|---|
| 1 | 选基础镜像：华为官方 **CANN Docker 镜像**（已含驱动+Toolkit+PyTorch NPU） |
| 2 | 装推理框架：在容器里装 vLLM |
| 3 | **挂载模型**：`-v ./models:/models`，避免每次重新下载 |
| 4 | 启动服务：`-p 8000:8000` 映射端口 |

**docker-compose.yml**：
```yaml
services:
  deepseek:
    image: ascendhub/cann-pytorch:latest
    devices:
      - /dev/davinci0          # 挂载 0 号 NPU
    volumes:
      - ./models:/models
    ports:
      - '8000:8000'
    command: vllm serve /models/DeepSeek-7B --dtype float16
```

### 显存估算公式（很实用）

```text
模型权重显存 = 参数量 × 每参数字节数

KV Cache 显存 = 2 × 层数 × kv头数 × 头维度 × 序列长度 × 并发数 × 字节数
```

**实际总需求 = 权重 + KV Cache + 运行时开销**，建议预留 **20%** 余量。

**算一笔账（Qwen2.5-7B，FP16）**：
```text
权重：14 GB
单请求 4096 上下文 KV Cache：512 MB
Atlas 300I（16GB）剩余：约 2GB
→ 只能支持约 4 个并发请求
→ 改用 INT8：权重 7GB，剩余 9GB → 并发提升一倍多
```

> 🎯 **这就是量化在部署侧的真实价值** —— 不只是省显存，而是**直接决定能扛多少并发**。

### 四项性能优化

| 优化 | 做法 | 效果 |
|---|---|---|
| **批处理** | `--max-num-seqs` 控制并发 | 提高利用率 |
| **KV Cache** | `--max-model-len` **别设太大** | 给并发留空间 |
| **量化** | INT8/INT4 | 省显存提并发 |
| **前缀缓存** | 共享 System Prompt | 避免重复计算 |

> 💡 **`--max-model-len` 别设太大**这条很反直觉但有道理：
> 如果业务对话通常不超过 2048 token，就别设成 8192。最大长度越长，预留给 KV Cache 的空间越大，能服务的并发就越少。

## ❓ 自测

1. Docker 容器和虚拟机最本质的区别？
2. 镜像和容器的关系？
3. 昇腾开发最常见的版本问题是什么？
4. vLLM 的 PagedAttention 解决了什么？
5. 为什么 `--max-model-len` 不该设置太大？

<details>
<summary>参考答案</summary>

1. 容器共享宿主机内核，虚拟机每个都带完整操作系统；因此容器更轻、启动更快。
2. 镜像是只读模板（类），容器是镜像的运行实例（对象）。
3. torch 与 torch_npu 版本必须严格一致，版本不匹配是昇腾开发最常见的错误来源。
4. 传统框架按请求预分配 KV Cache 导致显存碎片化；PagedAttention 把 KV Cache 分页按需分配，显存利用率提升 2-4 倍。
5. 最大序列长度越大，需要预留的 KV Cache 空间越多，留给并发请求的空间就越少，降低吞吐能力。
</details>
