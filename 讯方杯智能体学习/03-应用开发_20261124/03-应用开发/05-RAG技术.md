## 🎬 一、RAG 要解决什么

![[905-RAG三阶段.mp4]]

### 大模型的三个天生缺陷

| 缺陷 | 说明 |
|---|---|
| **时效性** | 知识截止于训练时间 |
| **覆盖性** | 训练数据没涵盖的领域/私有数据 |
| **幻觉** | 不知道就编 |

> **解决方案**：给模型**外挂知识库**，回答问题前先检索 —— **开卷考试**。

### 三个阶段

```text
① 索引   文档加载 → 分块 → 向量化 → 存入向量数据库
② 检索   用户问题向量化 → 相似度计算 → Top-K
③ 生成   问题 + 检索片段 → 组装提示词 → 模型生成
```

> 💡 **"至少两个阶段和向量有关"** —— 索引时向量化，检索时算相似度。

### 什么是向量

一串数字，表示文本的语义：

```text
"长沙" = [0.8, -0.3, 0.5, 0.34, ...]   （可以是几十到几千维）
```

**关键性质**：意思相近的文本，向量在空间中也相近。

## 🔍 二、三种检索方式（本章核心）

![[906-检索方式对比.mp4]]

### ① 关键字检索

**做法**：事先建关键字索引，检索时直接查找匹配的关键字。

| 优点 | 缺点 |
|---|---|
| **速度快** | 关键字有歧义时不准 |
| 指向明确时结果准 | 语义不同的内容会误判 |

### ② 全文检索

**做法**：对所有词汇建索引，查询时先分词，再在整个文本中找匹配文档。

**算法**：BM25、TF-IDF。

| 优点 | 缺点 |
|---|---|
| 比关键字更准 | 停留在**词级匹配** |
| 考虑了整体内容 | 无法理解语义深层关联 |

> 💡 **典型局限**：查"计算机"找不到写"电脑"的文档 —— 除非显式配同义词库。

### ③ 向量相似度检索

**做法**：把问题和文档都转成向量，比空间距离。

| 优点 | 缺点 |
|---|---|
| **语义级理解** | 向量是**黑盒**，结果难解释 |
| 能捕捉同义词、上下义 | 可能匹配到意思相近但不相关的 |

**典型场景**：
```text
查询："如何修复笔记本故障"
文档："电脑主板维修指南"
→ 词不一样，但语义相似，向量检索能匹配 ✅
```

### 三者对比

| | 关键字 | 全文（BM25） | 向量 |
|---|---|---|---|
| 匹配层面 | 词 | 词/短语 | **语义** |
| 可解释性 | 高 | 高 | **低** |
| 语义理解 | 无 | 弱 | **强** |
| 精确匹配 | 强 | 强 | 弱 |

> 🎯 **结论：混合架构**
> ```text
> 传统检索（关键词 + 精确匹配）+ 语义检索（向量 + 模糊匹配）
> ```
> 兼顾**效率、准确性和语义理解**。这是生产环境的标配。

## 🗄️ 三、向量数据库

### 为什么需要它

```text
索引时要存大量向量    → 谁来存？
检索时要算相似度      → 谁来算？
```

### 主流选择

| 数据库 | 特点 | 适合 |
|---|---|---|
| **Chroma** | 轻量、易集成，LangChain 原生支持 | **小中型项目、实验** |
| **Faiss** | Meta 出品，高性能，GPU 加速 | 大规模、图像检索 |
| **Milvus** | 国产分布式，亿级向量 | 企业生产 |
| **Pinecone** | 云服务，闭源 | 免运维 |

> 💡 **选型建议**：课程实验和小型项目用 **Chroma 或 Faiss** 就够。

## 📊 四、RAG 评估（本章最有价值的部分）

### 为什么必须评估

| 原因 | 说明 |
|---|---|
| **输出不确定** | 大模型本身有随机性 |
| **要衡量改进** | 置信度是升了 10% 还是降了 5%？ |
| **知识库动态变化** | 新知识可能带来干扰 |
| **模型选型需要** | 换模型/升级版本效果如何 |

### 评估的四个输入

| 输入 | 含义 |
|---|---|
| **question** | 用户问题 |
| **answer** | RAG 生成的答案 |
| **context** | 检索到的上下文 |
| **reference_answer** | 标准答案（需人工标注） |

### 四个核心指标 ⭐

**RAG 有两个组件：检索器 + 生成器，指标也分两组。**

#### 检索评估

**① context_recall（上下文召回率）**

> 上下文中**覆盖了参考答案关键信息的比例**。

```text
问题：《三体》的作者是谁？哪一年出版？
参考答案：刘慈欣，2006 年
上下文：刘慈欣，中国科幻作家，2006 年开始连载《三体》

→ 两个关键信息都在 → 召回率 = 100%
→ 若只提"刘慈欣"没提"2006 年" → 50%
```

**② context_precision（上下文精度）**

> 上下文中**相关内容所占的比例**。

```text
问题：苹果公司总部在哪里？
上下文：苹果成立于 1976 年，总部位于库比蒂诺，CEO 是库克，产品有 iPhone...

→ 只有"库比蒂诺"相关，其余 3 项无关
→ 精确率 = 1/4 = 25%
```

#### 响应评估

**③ faithfulness（忠实度）**

> 答案是否**完全基于上下文**，没有捏造或矛盾。

```text
问题：爱因斯坦哪年获诺奖？
答案：1921 年因光电效应研究获诺贝尔物理学奖
上下文：1921 年诺贝尔物理学奖得主爱因斯坦，理由为发现光电效应定律
→ 所有信息都有依据 → 忠实度 100%

反例：答案里加了"他当时在普林斯顿任教"（上下文没提）
→ 即使是真的，也算不忠实 → 忠实度下降
```

> 🎯 **注意这个细节**：判断标准是**"上下文里有没有依据"**，不是"事实对不对"。
> 这是忠实度和准确性的关键区别。

**④ answer_relevancy（答案相关性）**

> 答案是否**直接回答了问题**（不管对错）。

```text
问题：如何煮咖啡？
答案：咖啡豆需研磨至中粗，用 90℃ 热水冲泡 3 分钟
→ 直接回答方法 → 相关性高

反例：答案说"咖啡豆起源于埃塞俄比亚"
→ 回答了"起源"不是"方法" → 相关性低
```

### 四指标一张表

| 指标 | 归属 | 衡量什么 |
|---|---|---|
| context_recall | **检索** | 该找的都找到了吗 |
| context_precision | **检索** | 找到的有多少相关 |
| faithfulness | **生成** | 答案有没有依据 |
| answer_relevancy | **生成** | 答案切不切题 |

## 🛠️ 五、评估工具

### Ragas（主流）

> 专门评测 RAG 管道的框架，支持 LangChain 和 LlamaIndex。

```python
from ragas import evaluate
from ragas.metrics import (
    context_precision, context_recall,
    faithfulness, answer_relevancy
)
```

> 💡 Ragas 的 context_precision 略有不同：它计算每个相关块位置的 Precision@k，**更接近 MAP 指标**，反映排序质量。

### TruLens

相对独立，可集成到 LangChain / LlamaIndex，用"反馈函数"衡量相关性、适用性、有害性。

## 🩺 六、按指标诊断问题（超实用）

![[09-RAG应用评估和工具/幻灯片30.PNG]]

> **这一节是本章精华：看到低分，知道该改哪里。**

| 指标低 | 可能原因 | 该改谁 |
|---|---|---|
| **context_recall 低** | 知识库缺文档、Embedding 语义匹配不足 | **检索器** |
| **context_precision 低** | 返回大量无关文档、索引策略有误、相关文档排名低 | **检索器** |
| **faithfulness 低** | 提示词没要求"基于提供的信息回答"、上下文过长信息稀释 | **生成器** |
| **answer_relevancy 低** | 没理解问题意图、上下文与问题关联弱 | **生成器** |
| **四个都低** | 系统性问题 | 先查检索 |

### 优化顺序：先检索，再生成 ⭐

> **核心原则：先固根基，再求精进。**
>
> 理由：
> 1. **依赖关系** —— 生成质量上限受限于检索质量（Garbage In, Garbage Out）
> 2. **成本效益** —— 优化检索（调参、混合检索、重排序）比微调生成模型更快更便宜

### 具体优化手段

**提升 context_recall**：

| 手段 | 做法 |
|---|---|
| 混合检索 | BM25（症状术语）+ 向量（相似病例） |
| **查询改写** | "如何治疗糖尿病" → "药物治疗方案" + "饮食管理方法" |
| 知识库优化 | 去重去广告、定期增量更新 |

**提升 context_precision**：

| 手段 | 做法 |
|---|---|
| **重排序** | 检索结果二次排序 |
| 分块策略 | 语义分块、调整块大小 |
| 检索参数 | 调 Top-K、相似度阈值、混合权重 |

**提升 faithfulness**：

| 手段 | 做法 |
|---|---|
| 提示词约束 | 明确"仅基于提供的上下文回答" |
| **事实核查** | 生成后用 LLM 二次验证 |
| 上下文截断 | 保留开头结尾关键信息（防 Lost in the Middle） |
| 元数据增强 | 加标题、关键词帮助定位 |

**提升 answer_relevancy**：

| 手段 | 做法 |
|---|---|
| 问题分类 | 事实型/比较型/建议型 → 不同结构化提示 |
| 多轮追问 | "是否需要更详细的解释？" |
| 摘要压缩 | 去冗余再输入 |

### 指标阈值参考

| 指标 | 理想 | 危险线 |
|---|---|---|
| faithfulness | ≥ 0.85 | < 0.7 有严重幻觉 |
| answer_relevancy | ≥ 0.8 | < 0.6 用户难接受 |
| context_recall | ≥ 0.7-0.8 | —— |

**按行业分**：

| 行业 | 核心指标 |
|---|---|
| **医疗/法律**（高风险） | faithfulness ≥ 0.9，context_recall ≥ 0.9 |
| **客服/电商** | answer_relevancy ≥ 0.8，precision ≥ 0.7 |
| **通用问答** | answer_relevancy ≥ 0.7，recall ≥ 0.7 |

### F1 分数：平衡精度与召回

当 recall 和 precision 一高一低、难以判断时，用 F1（调和平均）：

```text
第一组：recall=0.6667, precision=0.4511
第二组：recall=1.0000, precision=0.3869
→ 算 F1 比较哪个整体更优
```

### 分块大小怎么定

**没有万能值，必须实测。**

| 场景 | 建议 |
|---|---|
| 通用 | **128-512 tokens** |
| 技术文档/论文 | 200-300（保术语完整） |
| 长叙事（小说） | 500-1000（保情节连贯） |
| 社交媒体短文本 | 100-200 |

> 🎯 课程实测案例：`chunk_size=128` 时 **F1 最高**、忠实度和相关性都处于高位，**且成本最低**。
> 大分块在召回上有优势，但 context_precision 显著下降、F1 降低 —— 说明引入了过多无关信息。

## ❓ 自测

1. RAG 解决大模型的哪三个问题？
2. 三种检索方式各自的优劣？
3. 上下文召回率和上下文精度的区别？
4. 忠实度和答案准确性有什么区别？
5. 为什么优化要先检索后生成？
6. 四个指标都低说明什么？

<details>
<summary>参考答案</summary>

1. 时效性（知识过时）、覆盖性（缺私有/专业领域知识）、幻觉。
2. 关键字检索快但怕歧义；全文检索更准但仍停留在词级；向量检索懂语义但不可解释、可能匹配到相近却不相关的。
3. 召回率看"该找到的关键信息找到了多少"，精度看"找到的内容里有多少是相关的"。
4. 忠实度看答案是否有上下文依据（即使事实正确，上下文没提也算不忠实）；准确性看事实本身对不对。
5. 因为生成质量的上限受检索质量限制（Garbage In Garbage Out），且优化检索成本更低见效更快。
6. 系统性问题，应先从检索环节查起。
</details>
