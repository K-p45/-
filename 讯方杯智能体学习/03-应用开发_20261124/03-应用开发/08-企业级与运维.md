## 🎬 一、Workflow vs Agent 选型

![[909-企业级架构与监控.mp4]]

| | Workflow | Agent |
|---|---|---|
| 流程 | **固定**，预定义 | **动态**，自主规划 |
| 优势 | 稳定、可预测、易调试 | 灵活、能处理未知情况 |
| 劣势 | 无法应对意外 | 不确定、难调试 |
| 适合 | 步骤明确的任务 | 开放式任务 |

### 一个非常好用的经验法则 ⭐

> **如果能画出完整的流程图 → 用 Workflow。**
> **如果无法穷举所有可能的路径 → 用 Agent。**

### 混合架构（真实项目标配）

```text
Workflow 处理标准流程（意图分类 → 信息提取 → 结果格式化）
        ↓
在需要灵活决策的环节嵌入 Agent 节点
```

兼顾**稳定性**和**灵活性**。

## 🔧 二、Dify 自定义工具

### 三类工具

| 类型 | 灵活度 |
|---|---|
| 内置工具 | 最固定（搜索、天气等） |
| **自定义 API 工具** | **最灵活** ⭐ |
| 知识库检索 | 固定 |

### 创建两步走

**第一步：写 API 服务**（用 FastAPI 等实现一个 HTTP 接口）

**第二步：写 OpenAPI Schema 描述它**

```yaml
openapi: '3.0.0'
info:
  title: 订单查询API
  version: '1.0'
paths:
  /api/order:
    get:
      summary: 查询订单状态
      parameters:
        - name: order_id
          in: query
          required: true
          description: 订单编号          # ← 模型靠这个理解参数
          schema: { type: string }
```

> 🎯 **`description` 字段是模型理解参数含义的唯一依据**，必须写清楚。
> 这和 Function Calling 里的工具描述是同一个道理（见 [[06-Agent与工具]]）。

## 🔄 三、两种推理模式

Dify 支持 **ReAct** 和 **Function Calling** 两种 Agent 模式。

| | ReAct | Function Calling |
|---|---|---|
| 过程 | **显式输出**思考→行动→观察 | 直接输出函数调用 |
| 优点 | 过程透明、可调试 | 更快、延迟低 |
| 缺点 | 每步一次 LLM 调用，**延迟高** | 过程不透明 |
| 适合 | **多步推理**（综合分析多数据源） | **简单直接**（查天气、查订单） |

> 🎯 **选型建议**：简单直接的任务用 Function Calling，需要多步推理的用 ReAct。

## 👥 四、多 Agent 协同的四种模式

![[15-多智能体协同与企业级应用设计/幻灯片13.PNG]]

| 模式 | 结构 | 适合 |
|---|---|---|
| **主从模式**（Master-Worker） | 主 Agent 分解任务+汇总，多个工作 Agent 执行 | 任务可清晰分解 |
| **管道模式**（Pipeline） | 按序处理，前一个输出是后一个输入 | 流程固定 |
| **竞争模式**（Voting） | 多个 Agent 独立处理，投票选最佳 | 对质量要求高 |
| **协作/协商模式** | Agent 之间讨论协商 | 需要权衡的场景 |

**举例**：
- 主从：主 Agent 把"撰写市场分析报告"拆成"收集数据""分析趋势""撰写结论"
- 管道：文本提取 Agent → 翻译 Agent → 摘要 Agent

### Python Orchestrator 编排

除了在 Dify 里拖拽，也可以用代码编排：

```python
class Orchestrator:
    def __init__(self):
        self.vision_agent_url = 'http://...'
        self.text_agent_url = 'http://...'

    def route(self, user_input):
        # 根据输入类型分发到不同 Agent
        ...
```

> 💡 **适合需要复杂控制逻辑的场景**，灵活性比平台内编排更高。

## 📊 五、监控与运维（本章重点）

### 为什么要结构化日志

> 纯文本日志（`2024-01-01 User asked a question`）在大规模系统中**很难检索分析**。

**改用 JSON**，每条日志是一个带明确字段的数据对象。

### 关键字段

| 字段 | 作用 |
|---|---|
| **trace_id** | 全链路追踪 ID（UUID），关联一个请求的所有日志 |
| **timestamp** | 毫秒级时间戳 |
| **path** | API 路径 |
| **latency_ms** | 处理时长（**核心性能指标**） |
| **status** | 状态码 |

```python
import logging, json

class JsonFormatter(logging.Formatter):
    def format(self, record):
        return json.dumps({
            "timestamp": self.formatTime(record),
            "level": record.levelname,
            "message": record.getMessage(),
        })
```

### TraceID 全链路追踪

```text
生成：请求进入的第一个入口（网关/中间件）生成 UUID
传递：通过 HTTP 头 X-Trace-Id 一路透传
使用：出问题时用 TraceID 搜索 → 看到每个环节的耗时、输入输出、错误
```

> 🎯 **一句话**：**TraceID 把一个请求散落在各服务中的日志串成一条线。**
> 没有它，排查一个跨 5 个服务的请求基本等于大海捞针。

### 四个核心性能指标 ⭐

| 指标 | 含义 | 目标 |
|---|---|---|
| **TTFT**（首 Token 时间） | 从请求到返回第一个 token | **交互场景 < 1 秒** |
| **TPS**（每秒 Token 数） | 生成速度 | 7B 单卡 30-60 TPS |
| **P99 延迟** | 99% 请求的完成时间 | 比平均更能反映真实体验 |
| **QPS** | 每秒请求数 | 容量规划依据 |

> 💡 **为什么看 P99 不看平均**：平均值会被大量快请求拉低，掩盖了慢请求的问题。**用户抱怨的永远是那 1%。**

### 告警策略

**核心矛盾**：太灵敏 → 告警疲劳；太迟钝 → 错过问题。

| 告警类型 | 阈值示例 |
|---|---|
| **慢请求** | `latency_ms > 2000` |
| **错误率** | 5xx 比例 > 1%（5 分钟窗口） |
| **资源** | NPU 显存 > 90%、温度 > 85°C |
| **成本** | 当日 token 消耗超预算 80% |

> 💡 **成本告警**在企业级应用中非常重要 —— 大模型的费用可能一夜之间失控。

### FastAPI 中间件实现监控

**中间件的优势**：在每个请求前后自动执行，**不需要改业务代码**。

```python
from starlette.middleware.base import BaseHTTPMiddleware

class OpsMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        trace_id = str(uuid.uuid4())
        start = time.time()
        response = await call_next(request)
        latency = (time.time() - start) * 1000
        # 记录 trace_id / latency / status
        return response
```

> 🎯 **这是「非侵入式」监控的典型做法** —— 业务代码一行不改，横切关注点（日志、追踪、限流）全在中间件里完成。

## ❓ 自测

1. 什么时候该用 Workflow，什么时候用 Agent？
2. ReAct 和 Function Calling 两种模式怎么选？
3. TraceID 解决了什么问题？
4. 为什么监控要看 P99 而不是平均延迟？
5. 为什么告警策略要平衡灵敏度和噪音？

<details>
<summary>参考答案</summary>

1. 能画出完整流程图（路径可穷举）用 Workflow；无法穷举所有可能路径用 Agent。
2. 简单直接的任务（查天气、查订单）用 Function Calling 更快；需要多步推理分析多个数据源的用 ReAct，过程透明可调试。
3. 把一个请求散落在多个服务、组件中的日志串联成完整链路，便于快速定位问题根因。
4. 平均值会被大量快速请求掩盖，P99 反映最慢的那 1% 用户的真实体验，而用户抱怨的正是这部分。
5. 太灵敏会产生大量误报导致"告警疲劳"、忽略真正的问题；太迟钝则会错过故障。
</details>
