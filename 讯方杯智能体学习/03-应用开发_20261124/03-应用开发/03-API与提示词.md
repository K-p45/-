## 🎬 一、API：一套接口通吃所有模型

![[903-API调用要点.mp4]]

### 什么是 API

> 像**餐厅服务员**：你不需要进厨房，只要告诉服务员要什么，它传达给后厨，再把菜端上来。

### HTTP 请求的四个部分

```text
POST /v1/chat/completions          ← 请求行（方法 + 路径）
Authorization: Bearer sk-xxx       ← 请求头（认证）
Content-Type: application/json     ← 请求头（类型）

{ "model": ..., "messages": [...] } ← 请求体（JSON）
```

### 最重要的一点：OpenAI 兼容标准

> **国内外几乎所有主流模型都兼容 OpenAI 接口。**

```text
学到一套 → 通吃所有
换模型只需改两个参数：base_url + api_key
```

| 平台 | base_url |
|---|---|
| DeepSeek | `https://api.deepseek.com` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| 本地 vLLM | `http://localhost:8000/v1` |

> 🎯 **这是本章最有价值的一句话**。
> 学会调 DeepSeek，改个地址就能调通义、调本地部署的模型，**代码一行不用改**。

### 消息格式：三种角色

| 角色 | 作用 |
|---|---|
| **system** | 系统提示，设定模型行为 |
| **user** | 用户输入 |
| **assistant** | 模型的历史回复 |

### 核心参数

| 参数 | 作用 | 建议 |
|---|---|---|
| **model** | 选模型 | `deepseek-chat` 通用 / `deepseek-reasoner` 推理 |
| **messages** | 对话数组 | 见上方三种角色 |
| **temperature** | 随机性 0-2 | 客服 0.3-0.5，创作用 0.8-1.0 |
| **max_tokens** | 输出长度上限 | 太小会截断，太大会浪费 |
| **top_p** | 核采样 | 0.9 只从累计概率前 90% 采样 |

> ⚠️ **中文 1 个字 ≈ 1.5-2 个 token**，估成本时别忘了这个换算。

### HTTP 状态码（排错必备）

| 码 | 含义 | 怎么办 |
|---|---|---|
| **200** | 成功 | —— |
| **400** | 请求格式错 | 检查 JSON、参数范围（如 temperature>2） |
| **401** | 认证失败 | API Key 无效/过期/没传 |
| **429** | 频率超限 | 降频，或按 `Retry-After` 头等待 |
| **500** | 服务端错误 | 通常是临时的，重试 |

### Token 与成本

```text
成本 = 输入 Token × 输入单价 + 输出 Token × 输出单价
```

**DeepSeek 价格**：

| 模型 | 输入 | 输出 |
|---|---|---|
| deepseek-chat | 1 元/百万 | 2 元/百万 |
| deepseek-reasoner | 4 元/百万 | 16 元/百万 |

> 💡 用 `tiktoken` 库可以精确算 token 数。

### 最小可用代码

```python
from openai import OpenAI

client = OpenAI(
    base_url='https://api.deepseek.com',
    api_key='sk-xxx'                      # 从环境变量读，别硬编码
)

resp = client.chat.completions.create(
    model='deepseek-chat',
    messages=[
        {'role': 'system', 'content': '你是一个有帮助的助手'},
        {'role': 'user', 'content': '你好'}
    ]
)
print(resp.choices[0].message.content)
```

## 🔄 二、进阶：多轮对话与流式

### 多轮对话的原理（重要）

> **大模型是无状态的** —— 它不记得上一次说了什么。

```python
messages = [{'role': 'system', 'content': '你是助手'}]

# 每一轮都把完整历史发过去
messages.append({'role': 'user', 'content': '你好'})
resp = client.chat.completions.create(model=..., messages=messages)
messages.append({'role': 'assistant', 'content': resp.choices[0].message.content})
```

> 🎯 **"无状态"这一点非常重要**。所谓多轮对话，其实是**每次都把全部历史重新发一遍**。
> 这直接带来了下面两个问题：token 消耗增加、可能超上下文窗口。

### 历史管理三策略

| 策略 | 做法 | 优缺点 |
|---|---|---|
| **固定窗口** | 只留最近 N 轮 | 简单，但会丢信息 |
| **Token 计数** | 接近上限时删最早的 | 更精确 |
| **摘要** | 把早期对话压成摘要 | 保留关键信息，多一次调用 |

> 💡 **System Prompt 永远不裁剪** —— 它是角色设定，删了模型就"失忆"了。

### 流式调用（体验关键）

**问题**：默认要等全部生成完才返回，用户干等。

**解法**：`stream=True`，边生成边返回，像打字机。

```python
resp = client.chat.completions.create(
    model='deepseek-chat', messages=messages, stream=True
)
for chunk in resp:
    print(chunk.choices[0].delta.content or '', end='')
```

**技术原理**：HTTP 的 **SSE（Server-Sent Events）**，服务端持续推送事件流。

> 💡 **第一个 token 几百毫秒就回来**，用户感知速度大幅提升。
> 注意流式时内容是 `delta` 字段，不是 `message`。

### 异步调用

批量处理时用 `AsyncOpenAI` + `asyncio`，避免阻塞。

### 错误处理与重试

**指数退避**：第一次等 1 秒，第二次 2 秒，第三次 4 秒……

```python
# openai 库内置自动重试，默认 2 次
client = OpenAI(max_retries=5, timeout=30)
```

### 用 FastAPI 做中间层

> 生产环境**不让前端直连大模型 API**，而是通过中间层转发。

为什么：
- 统一管理 API Key（不暴露给前端）
- 加业务逻辑、日志、限流
- 便于切换后端模型

### ngrok 内网穿透

开发阶段要让 Dify 等外部服务访问本地 API：

```bash
ngrok http 8000     # 得到 https://abc123.ngrok.io
```

> ⚠️ 免费版有带宽限制、URL 每次重启都变 —— **只适合开发，生产别用**。

### 六条最佳实践

1. **API Key 放环境变量**，绝不硬编码
2. **设置合理超时**（普通对话 30s，长文本 60-120s）
3. **优雅降级**：API 挂了给友好提示，或切备用模型
4. **记录日志**：输入/输出长度、延迟、token、错误
5. **控制并发**：用信号量避免 429
6. **System Prompt 认真写**（见下）

## 🎭 三、提示词工程

### System Prompt 四要素

| 要素 | 例子 |
|---|---|
| **角色定义** | 你是一位经验丰富的 Python 程序员 |
| **输出格式** | 以 Markdown 输出 / 返回 JSON，含 result 和 reason |
| **约束条件** | 不要编造不存在的 API；不确定就说不确定 |
| **示例** | 1-2 个输入输出示例 |

### 两种提示词结构（本章重点）

![[06-提示词工程应用与实践/幻灯片15.PNG]]

### ① 通用模型的「五层结构」

| 层 | 内容 |
|---|---|
| **角色** | 角色设定、背景、能力 |
| **场景要求** | 需求 / 目标描述 |
| **任务** | 可执行清单 |
| **示例** | 成功案例、失败反例、格式模板 |
| **约束** | 显性限制 + 偏好 + 风险规避 |

### ② 推理模型的「反直觉用法」⭐

> **对于推理模型（o1、DeepSeek-R1、QwQ、豆包深度思考），用通用模型的方式对话，效果可能极差。**

**为什么**：推理模型自己就会推理。你再告诉它"一步步想"，等于**让一个专家按你的思路走**，反而限制它。

**正确心法**（课程原话很生动）：
> **把它当成「一个能力很牛逼但不知道你想要什么的员工」。**
> 只需要告诉它 **我是谁 + 我的目标**，**不需要告诉它怎么做**。

```text
❌ 推理模型的坏提示词：
"请先分析条件，然后第一步计算…第二步…第三步…最后得出结论"

✅ 推理模型的好提示词：
"我是一名初中数学老师，需要给初二学生讲解这道题的解题思路。"
（然后直接给题目，让它自己组织推理）
```

**公式**：
```text
推理模型提示词 = 角色 + 背景信息（可选）+ 任务
```

### 推理模型的三个技巧

| 技巧 | 说明 |
|---|---|
| **1. 声明"我是谁"极其有用** | 看不懂专业输出时，说"我是初学者"，它就会换个讲法 |
| **2. 观察它的思考过程** | 思考过程会揭示它是怎么理解你的提示词的 |
| **3. 用推理模型帮你写提示词** | 让强模型写，再拿到普通模型上跑 |

> 🎯 **技巧 3 特别巧妙**：DeepSeek-R1 有深度思考能力，让它帮你设计提示词，然后拿去给没有深度思考能力的模型用。

### 提示词进阶技巧

| 技巧 | 说明 |
|---|---|
| **CoT 思维链** | 让它展示推理过程 |
| **自一致性** | 多次采样投票 |
| **ToT 思维树** | 探索多条路径 |

### 提示词攻击与防范

| 攻击类型 | 说明 |
|---|---|
| **提示词注入** | 用户输入里夹带指令，如"忽略之前所有规则" |
| **提示词泄露** | 诱导模型吐出 System Prompt |
| **越狱** | 绕过安全限制 |

**防范措施**：
- 系统提示检测
- 固定身份边界
- 输入过滤
- 敏感操作二次确认

1. 换用另一个厂商的模型，代码要改什么？
2. 为什么说"大模型是无状态的"？这对多轮对话意味着什么？
3. 流式调用用的什么协议？内容在哪个字段？
4. 对推理模型（如 DeepSeek-R1）写提示词有什么特殊要求？
5. 收到 429 该怎么办？

<details>
<summary>参考答案</summary>

1. 只需修改 base_url 和 api_key 两个参数，其他代码不用改。
2. 模型不保存任何对话记忆；所以多轮对话必须每次把完整历史重新发送，导致 token 消耗增加且可能超上下文窗口。
3. HTTP 的 SSE（Server-Sent Events）协议；内容在 delta 字段中（非流式是 message 字段）。
4. 不要教它怎么做，只需告诉它"我是谁 + 我的目标"，让它自己推理；过度指定步骤反而效果差。
5. 降低请求频率，按 Retry-After 等待，并实现指数退避重试（1s、2s、4s…）。
</details>
