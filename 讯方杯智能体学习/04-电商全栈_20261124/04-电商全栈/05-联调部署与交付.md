## 🎬 一、三方联调：前端 - 后端 - 数据库

![[1009-联调与交付.mp4]]

### 完整数据流的六步

```text
前端发起请求（带参数）
   → 后端路由接收
   → 后端执行 SQL 查询/写入
   → 数据库返回结果集
   → 后端组装结构化响应
   → 前端接收并渲染
```

> 🎯 **链路上任何一环断掉，联调就卡在对应位置** —— 所以第一步是**确认断在哪**。

### 启动服务后要看两行日志

| 日志 | 缺失说明 |
|---|---|
| 「数据库连接成功」 | `.env` 密码错 / MySQL 没启动 |
| 「服务器已启动 http://localhost:3000」 | 端口被占用 / 代码语法错误 |

> **两行都出现，才说明联调前置条件满足。**

### 接口契约：前后端约定的「语言」⭐

```js
if (data.code === 0) { /* 成功 */ }
```

> 这就是契约：**后端约定成功时 code 为 0，前端据此判断**。
> 任何一方私自改约定（比如改成 `"success"`），另一方会在**无感知的情况下失败**。

> ⚠️ **最隐蔽的问题：字段命名不一致**
> 后端返回 `product_id`，前端按 `productId` 取值 →
> **页面不报错，只是显示空白** —— 比直接报错更难排查。

### 同源策略与 CORS

**同源的三要素，必须全部相同**：

```text
协议 + 域名 + 端口
```

```text
前端 http://localhost:8080
后端 http://localhost:3000/api
→ 端口不同 → 跨域！
```

> 🎯 **这不是后端设置的，是浏览器内置的安全策略。**
> 目的是防止恶意网站利用用户在别的网站的登录凭证发起请求。

**跨域时的表现**：

| 现象 | 说明 |
|---|---|
| 页面**空白**或一直转圈 | 像是没返回数据 |
| **Console 有红色 CORS 报错** | 数据可能已经到了，但**被浏览器挡在脚本能读的范围外** |

> 💡 **"数据已经到了但读不到"** —— 这个细节能帮你少走很多弯路。

### localhost 陷阱 ⭐

| 环境 | `localhost` 指向 | 结果 |
|---|---|---|
| 电脑浏览器 | 电脑本机 | ✅ 成功 |
| 手机真机 | **手机自己** | ❌ 失败（手机上没跑后端） |

> **原因**：`localhost` 始终指向**当前设备自身**。
> **解法**：真机调试要用**电脑的局域网 IP**。

**排查思路**：先分清是**网络层**还是**代码层**问题。
```text
Network 里请求直接失败（拿不到状态码）→ 网络层（地址配置）
收到了 404 / 500 错误响应              → 代码层（逻辑）
```

### 请求模块封装：为什么要有 request.js

**封装前**：每个页面各写一遍 `uni.request`，各自判断 statusCode、各自弹 Toast。

**封装后**：
```js
const data = await request({ url: '/products' })
```

| 对比 | 无封装 | 有封装 |
|---|---|---|
| 请求写法 | 每页写 uni.request | 统一 `await request()` |
| 状态判断 | 每页判断 statusCode + code | 封装层统一判断 |
| 错误处理 | 每页写 showToast | 封装层统一提示 |
| **改错误文案** | 改所有页面 | **改一处** |
| **切环境** | 全项目搜 BASE_URL | **改一处** |

> 🎯 **最大的收益是「改一处」**：BASE_URL 从开发切到生产只改 request.js 一行。

## 🎬 二、测试：从 mock 到真实数据

### 商品列表联调

```js
// 之前：写死的数组
let goodsList = [...]

// 之后：真实请求
const { list } = await request({ url: '/products', data: params })
```

**关键点**：`params` 里的字段要**和后端 SQL 条件对应**。

| 前端传 | 后端 SQL |
|---|---|
| `category` | `AND category = ?` |
| `keyword` | `LIKE ?` |
| `page` / `limit` | `LIMIT ?, ?` |

### 订单创建：要验证三处数据变化 ⭐

前端收到"下单成功"只是说明**请求被处理了**，要验证订单真的生成了，必须查库：

| 表 | 变化 |
|---|---|
| **orders** | 新增一条订单记录 |
| **order_items** | 新增商品明细 |
| **products** | **库存被扣减** |

> 🎯 **三处必须都变** —— 这正是事务要保证的一致性的实际验证。

### 异常流程测试（这部分最容易被跳过）

**做法**：把购物车数量改成 **9999**（远超库存）再结算。

**测试目的**：**不是验证成功，而是验证"该失败时能否正确失败"**。

| 预期 | 说明 |
|---|---|
| 前端弹出"库存不足" | 错误提示正常展示 |
| **数据库不新增任何订单** | 事务正确回滚 |

> 💡 **如果点击结算后页面无响应或卡死** → 说明前端没处理异常分支。
> **排查方向不是业务逻辑，而是错误分支有没有被捕获。**

> 🎯 **这节课最重要的观念**：
> **正常人都会测成功路径，专业开发者测失败路径。**

## 🎬 三、项目交付：文档工程

### 「代码能跑」≠「项目能交付」

> 交付物不只是代码，还包括**让别人能看懂、能接手、能复现**的一套文档。

### 八份核心交付文档

| 文档 | 主要接收者 |
|---|---|
| **项目总 README** | 所有人（**入口**） |
| 需求规格说明书 | 客户、新成员 |
| 数据库设计文档 | 后端开发 |
| **API 接口文档** | 前后端开发 |
| 测试与联调报告 | 测试、验收 |
| 部署手册 | 运维、新人 |
| 用户操作手册 | 最终用户 |
| 项目总结报告 | 复盘 |

> 🎯 **看「接收者」这一列就明白了**：**不同文档面向不同的人**。
> 写部署手册时不能假设读者知道项目背景 —— 他要能**从零跑通**。

### 两种归档方案

| | 按实验阶段归档 | **按文档用途归档** |
|---|---|---|
| 目录 | 实验1~4 各一个 | 需求/设计/接口/测试/部署 |
| 优点 | 与课程对应，整理成本低 | **符合企业交付习惯** |
| 缺点 | 同类文档分散 | 与实验过程对应弱 |
| 适合 | 课程作业提交 | **对外交付** |

### 命名与目录规范

| 规范 | 说明 |
|---|---|
| **命名统一** | 不要 `database_design.md` 和「数据库设计说明书.docx」混用 |
| **版本可区分** | AI 生成的 candidate 确认后另存正式版 |
| **目录不堆根目录** | 分层，**不超过 3 层** |
| **文件名不用中文** | 避免跨平台编码问题 |
| **README 做索引** | 从 README 能到任何一份文档 |

### 文档与代码一致性核查 ⭐

**为什么会不一致**：文档先于代码产出，开发中需求调整、字段改名、类型修改——**没同步回文档**。

**三种典型偏差**：

| 偏差 | 例子 |
|---|---|
| 字段不一致 | 设计文档的字段 vs 最终 SQL 表结构 |
| 接口不一致 | 接口文档的路径/参数 vs 后端实际路由 |
| 页面不一致 | UI 说明的页面清单 vs pages.json 实际配置 |

> ⚠️ **这类问题很隐蔽**：文档本身语句通顺、格式规范，**表面看不出错**。

**五组必查对照**：

| 文档侧 | 代码侧 |
|---|---|
| database_design.md | database/ecommerce.sql |
| api_contract.md | 后端实际路由 |
| ui_spec.md | pages.json |
| 字段映射 | 前端字段取值 |

### 发现不一致怎么改？—— 判断原则

> **报告只告诉你"哪里不一致"，不告诉你"以哪边为准"。**

| 情况 | 判断 | 处理 |
|---|---|---|
| **文档过时** | 实现是对的，文档没跟上 | **改文档** |
| **代码缺陷** | 文档是对的，实现偏离了 | **改代码** |

> 🎯 **判断方法**：问自己"**哪边反映了真实业务意图？**"
> 联调时改了字段名 → 文档过时 → 改文档
> 文档定义了订单状态枚举，代码冒出个没定义的状态 → 代码缺陷 → 改代码

### 部署手册的验收标准

> **清空环境变量，严格按手册从零执行一遍，一次性成功，才算合格。**

**要求**：
- 每一步完整记录，**不假设读者有前置知识**
- 命令和配置项**取自工程真实文件**，不凭经验编造

## ❓ 自测

1. 联调前必须看到哪两行日志？
2. 为什么字段名不一致比报错更难排查？
3. 跨域被拦截时页面上表现是什么？为什么？
4. 真机调试为什么不能用 localhost？
5. 异常流程测试的目的是什么？
6. 发现文档和代码不一致，怎么判断改哪边？

<details>
<summary>参考答案</summary>

1. 「数据库连接成功」和「服务器已启动」两行，缺任一行说明前置条件未满足。
2. 因为不会报错，只是页面显示空白，看起来像"没数据"，需要去比对前后端字段定义才能发现。
3. 页面空白或一直转圈；因为请求可能已经到达服务器并返回了数据，但响应被浏览器的同源策略拦截，脚本读不到返回内容。
4. localhost 始终指向当前设备自身，手机上的 localhost 指手机自己，而手机上并没有运行后端服务。
5. 验证系统在应该失败时能否正确地失败——提示错误、且数据库不产生脏数据，而不是验证成功路径。
6. 判断哪边反映真实业务意图：如果是联调中改了实现但文档没跟上，就改文档；如果是实现偏离了文档定义，就改代码。
</details>
