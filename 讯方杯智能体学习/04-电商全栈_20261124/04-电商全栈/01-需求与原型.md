## 🎬 一、需求分析要回答三个问题

![[1001-需求分析三问.mp4]]

| 问题 | 具体内容 |
|---|---|
| **谁用？** | 三类角色：普通用户、商家、管理员 |
| **做什么？** | 每类用户能执行哪些操作 |
| **做到什么程度？** | 优先级 P0/P1/P2 + 业务规则 |

### 三类用户与权限边界 ⭐

| 角色 | 职责 | 功能边界 |
|---|---|---|
| **普通用户（买家）** | 浏览、加购、下单、支付、查看订单 | 只能操作**自己的**数据 |
| **商家** | 发布/编辑商品、上下架、看订单与销售数据 | **只能管理自己发布的**商品（`seller_id` 控制） |
| **管理员** | 管理所有商品和订单、管理用户、运营 | 全平台 |

> 🎯 **为什么权限边界这么重要**：
> 如果商家能篡改他人商品，或买家能窥探别人订单——**整个交易信任体系瞬间崩塌**。
> 所以三者**功能边界清晰，数据权限相互隔离**。

### 核心业务规则（这才是需求的灵魂）

**购物车与库存**：

| 规则 | 说明 |
|---|---|
| 重复加购 | 数量**累加**，不重复添加 |
| 库存上限 | 数量不能超库存，超了明确提示"库存不足，最多可购 N 件"，**不静默截断** |
| 售罄 | 库存为 0 时显示"已售罄"，加购按钮**禁用** |
| 与账户绑定 | 登录后从数据库读取 |
| 清空时机 | 提交订单后，已下单商品自动清空 |

**订单与支付**：

| 规则 | 说明 |
|---|---|
| **金额重算** | 由**后端**根据价格数量重新计算，**不信任前端传入的金额** |
| **价格快照** | 下单时记录商品名称和单价，后续商品变化不影响已有订单 |
| **库存扣减** | 提交时校验并扣减，库存不足拒绝下单 |
| **状态流转** | 待支付 → 已支付 → 已发货 → 已完成（**不可逆**） |
| 取消订单 | 仅待支付可取消，取消后**释放库存** |

> 🎯 **「不信任前端传入的金额」这一条是安全底线**。
> 如果后端直接采用前端传来的金额，用户改个请求就能一分钱买东西。

> 💡 **「价格快照」解决的是历史数据一致性问题**：
> 商品今天卖 100，明天涨到 150。如果订单只存 product_id，那查历史订单会显示 150——**但用户当时确实付了 100**。

### 数据实体识别

**方法**：从功能倒推 → 每个功能背后对应什么存储需求。

| 实体 | 核心字段 |
|---|---|
| **users** | user_id, username, phone, password_hash, role |
| **products** | product_id, name, price, stock, category_id, image_url, status, **seller_id** |
| **cart** | cart_id, user_id, product_id, quantity（**独立表**，不与订单复用） |
| **orders** | order_id, user_id, order_no, total_amount, status, address |

> 💡 **cart 为什么是独立表**：购物车是"暂存"，订单是"已成交"。混用一张表会导致状态混乱。

### AI 在需求分析中的边界

| AI 能做 | AI 不能做 |
|---|---|
| 快速整理功能清单 | ❌ 替你做优先级决策 |
| 识别遗漏的业务规则 | ❌ 替你确认业务规则是否正确 |
| 生成文档初稿 | ❌ 替你判断技术方案是否适合 |
| 提供选型建议 | |

> 🎯 **正确模式：AI 出建议，人做决策。**

## 🎬 二、原型设计

![[1002-原型与页面清单.mp4]]

### 核心价值

> 在**正式开发之前**，用最低成本验证设计方案。

```text
原型：制作周期以天/小时计，修改成本几乎为零
开发：动辄数周，上线后修改成本高昂
```

### 两大类产出

| 类型 | 特点 | 用途 |
|---|---|---|
| **低保真** | 黑白线框图，关注布局 | 快速验证功能模块是否齐全 |
| **高保真** | 真实颜色/字体/图标/图片 | 接近最终产品，可用于用户测试 |

**另一个维度**：
- **静态原型**：只展示布局，无真正跳转
- **可交互原型**：有页面跳转、按钮反馈

### 电商的五个关键页面

| 页面 | 核心元素 |
|---|---|
| **首页/商品列表** | 搜索栏、分类导航、商品卡片（图+名+价+销量，**双列网格**） |
| **商品详情** | 大图、价格与库存状态、描述、加购与立即购买 |
| **购物车** | 复选框+图片+名称+单价、数量步进器（**超库存禁用**）、清空、合计 |
| **确认订单** | 收货地址、商品清单、实付金额、提交按钮 |
| **支付页** | 金额展示、支付方式、支付按钮与结果反馈 |

### 原型验收清单 ⭐

> 这张表的价值在于：**它把"感觉差不多了"变成了可检查的项。**

| 维度 | 验收要点 |
|---|---|
| **页面完整性** | 用户端 10 个 + 商家端 3 个 + 管理端 5 个 |
| **功能点覆盖** | 首页有搜索/分类/卡片，购物车有修改/删除/清空/结算 |
| **交互流程** | 点卡片能进详情？加购有反馈？支付成功跳订单列表？ |
| **状态处理** | 空状态（购物车空/订单空）、加载状态、错误状态（Toast） |
| **角色与权限** | 普通用户看不到商家/管理 Tab；未登录跳转登录页 |
| **业务规则落地** | 超库存被阻止、库存 0 时按钮禁用、状态流转正确 |

> 🎯 **「状态处理」这一项最容易被漏掉**。
> 新手只做"正常情况"，结果购物车为空时页面一片空白、加载时卡住没提示。

### AI 在原型设计中的协作模式

```text
AI 生成方案 → 人选择决策 → AI 细化落地 → 人验收确认
```

| 环节 | AI 负责 | 人负责 |
|---|---|---|
| 方案生成 | 生成多套 UI 方案 | 根据业务定位选择 |
| 设计规范 | 输出规范文档 | 审核确认 |
| 原型生成 | 生成可交互 HTML | **逐页验收并指出具体问题** |
| 修改打磨 | 快速修改局部 | 确认是否达标 |

1. 需求分析要回答哪三个问题？
2. 为什么订单金额必须后端重算？
3. 什么是价格快照？解决什么问题？
4. 购物车超过库存时应该怎么提示？为什么不能静默截断？
5. 原型验收的六个维度是什么？

<details>
<summary>参考答案</summary>

1. 谁用这个系统、每类用户能做什么、做到什么程度（优先级和业务规则）。
2. 因为前端传入的数据可以被篡改，如果后端直接采用，用户改请求就能少付钱。
3. 下单时把商品名称和单价记录到订单里；解决商品后续调价导致历史订单金额显示错误的问题。
4. 明确提示"库存不足，最多可购 N 件"；静默截断会让用户以为按自己选的数量下单了，产生误解。
5. 页面完整性、功能点覆盖、交互流程、状态处理、角色与权限、业务规则落地。
</details>
