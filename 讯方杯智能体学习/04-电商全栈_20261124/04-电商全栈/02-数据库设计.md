# 项目二 · 环境搭建与数据库设计

> **一句话**：数据库设计就是**把业务问题翻译成表结构和约束**。
> 约束越严格，数据越可信。

## 🎬 一、从业务到实体

![[1003-数据库四个核心实体.mp4]]

### 四个核心实体

| 实体 | 回答什么 |
|---|---|
| **users** | 谁在买 |
| **products** | 卖什么 |
| **orders** | 一次交易 |
| **order_items** | 交易里有哪些商品 |

### 三种关系怎么表达

**一对多**：**外键放在「多」的一方**。

```text
用户 → 订单（一个用户多个订单）
  → user_id 放在 orders 表，指向 users

订单 → 订单详情（一个订单多条详情）
  → order_id 放在 order_items 表，指向 orders
```

**多对多**：**必须用中间表拆成两个一对多**。

```text
订单 ↔ 商品（多对多）
  → 用 order_items 中间表
  → 通过 order_id 和 product_id 两个外键各指一方
```

> 🎯 **多对多为什么不能直接用外键**：两张表之间的外键只能记录**单一方向**的归属，装不下双向往返的"多个对多个"。

**order_items 为什么必须单独存在**：

| 字段 | 记录什么 |
|---|---|
| quantity | 买了多少 |
| **unit_price** | **下单时的单价**（价格快照！） |
| subtotal | 小计 |

> 💡 如果把这些塞进 orders 表，一个订单只能记录一种商品 —— 而现实是一个订单常有多件商品。

## 🎬 二、范式：拆表的三个层次

![[1004-三范式与反范式.mp4]]

| 范式 | 要求 | 反例 |
|---|---|---|
| **1NF** | 字段**原子性** | 地址全塞一个字段；"商品1,商品2"塞一个字段 |
| **2NF** | 非主键字段**完全依赖**整个主键 | 联合主键(订单ID+商品ID)，但"商品名称"只依赖商品ID |
| **3NF** | 非主键字段之间**不能互相依赖** | "商品分类"依赖"商品名称"而不是主键 |

**电商四张表本质上是按 3NF 设计的** —— 用户信息只在 users 存一份。

### 范式 vs 反范式（不是对错，是取舍）

| | 范式化 | 反范式化 |
|---|---|---|
| 目标 | 减少冗余、降低维护成本 | 提升查询效率 |
| 做法 | 用户信息只在 users 存一份 | orders 直接存 `total_amount` 汇总值 |
| 收益 | 改手机号只改一行 | 查询订单列表不用每次 SUM |
| 代价 | 查询要 JOIN 多张表 | 每次改详情都要同步更新，否则不一致 |

> 🎯 **判断标准**：
> - 数据一致性要求高、更新频繁（订单状态、用户信息）→ **范式化**
> - 查询量大、更新频率低（统计分析）→ **适度反范式**

### 范式与 JOIN 的关系

> 范式把大表拆成小表，**换来维护成本和一致性**；代价是查询要 JOIN 拼回来。

```text
"张三的订单里买了哪些商品"
  → 信息分散在 users、orders、order_items、products 四张表
  → 必须用 JOIN 重新拼接
```

### ER 图三要素

**顺序很重要**：先实体 → 再属性 → 最后关系。

> 💡 **ER 图和 DDL 是一一对应的**：图上定了"一个用户对应多个订单"，建表时 orders 表就必须有 user_id 外键。

## 🎬 三、建表的六个关键决策

![[1005-建表六个关键决策.mp4]]

### ① 字符集：必须 utf8mb4

```sql
CREATE DATABASE ecommerce_db
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;
```

> ⚠️ **MySQL 的 `utf8` 是阉割版** —— 最多 3 字节。
> 遇到 emoji（👍😂）或部分生僻汉字（4 字节）会**写入失败**。
> **utf8mb4 才是完整的 UTF-8**（mb4 = max bytes 4）。

### ② 主键与唯一约束

| 约束 | 写法 | 作用 |
|---|---|---|
| 主键自增 | `user_id INT PRIMARY KEY AUTO_INCREMENT` | 免手动指定，避免冲突 |
| 唯一 | `phone VARCHAR(20) UNIQUE` | 重复注册**数据库直接拒绝**，不用写查重代码 |
| 必填 | `username NOT NULL` | 缺失时数据库报错 |

### ③ 金额必须用 DECIMAL ⭐

```sql
price DECIMAL(10, 2)     -- 总共 10 位，小数点后 2 位
```

**为什么不能用 FLOAT/DOUBLE**：

| 数值 | DECIMAL | FLOAT（实际存储） |
|---|---|---|
| 7999.00 | 7999.00 | 7998.9999999 ❌ |
| 0.10 | 0.10 | 0.100000001 ❌ |
| 19.99 | 19.99 | 19.9900007 ❌ |

> 🎯 **浮点数在二进制中天然有精度误差**，累加几次误差就显现了。
> 金额出错的直接后果是**账务不一致** —— 这是不可接受的。
> **金额字段的唯一正确选择就是 DECIMAL。**

### ④ 状态字段用 ENUM

```sql
products.status ENUM('on_sale','off_sale','deleted')
orders.status   ENUM('pending','paid','shipped','completed','cancelled')
```

> 💡 **优势**：把取值校验**下沉到数据库层**，业务代码不用额外判断。
> 用 VARCHAR 能存任意字符串，非法值要靠代码拦 —— 而 ENUM 是数据库直接拦。

### ⑤ 时间字段自动维护

```sql
created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
```

| 字段 | 行为 |
|---|---|
| created_at | 插入时自动填入，**之后不再变** |
| updated_at | 每次 UPDATE 自动刷新，**不用手写 SET** |

> 💡 `DESCRIBE users` 时 Extra 列能看到 `DEFAULT_GENERATED` 和 `on update CURRENT_TIMESTAMP` —— 这是数据库层自动维护的直接证据，**不依赖任何业务代码**。

### ⑥ 外键级联策略：RESTRICT vs CASCADE ⭐

![[02-环境搭建与数据库设计/幻灯片30.PNG]]

| 策略 | 行为 |
|---|---|
| **RESTRICT** | 有关联记录时，**拒绝删除**并报错 |
| **CASCADE** | 删除主表记录时，**自动删除**关联子表记录 |

**电商里的两处不同选择**：

| 关联 | 策略 | 理由 |
|---|---|---|
| orders → order_items（订单→详情） | **CASCADE** | 订单删了，它的详情自然不用留 |
| products → order_items（商品→详情） | **RESTRICT** | 商品被订单引用过，**禁止删除**，保历史订单完整 |

> 🎯 **这个对比是本章最精妙的设计**。
> 如果商品也用 CASCADE，删一个商品会**连带删掉所有历史订单详情** ——
> 用户查过期订单时就不知道当时买了什么了。
>
> **正确做法**：商品下架用 `UPDATE status = 'off_sale'`，**而不是 DELETE**。

### 外键的价值：数据完整性最后防线

```sql
INSERT INTO orders (user_id, ...) VALUES (999, ...);
-- 若 999 不存在 → ERROR 1452，插入被拒绝
```

> 这就是阻止**「孤儿记录」**的机制。

## 🎬 四、SQL 查询：JOIN 与索引

![[1006-JOIN与索引.mp4]]

### SQL 三大分类

| 分类 | 作用 | 语句 |
|---|---|---|
| **DDL** | 定义结构 | CREATE / ALTER |
| **DML** | 操作数据 | INSERT / UPDATE / DELETE |
| **DQL** | 查询数据 | SELECT |

### JOIN 两种

| | INNER JOIN | LEFT JOIN |
|---|---|---|
| 右表无匹配 | **整行排除** | **保留左表行**，右表填 NULL |
| 场景 | 只要完整匹配的记录 | 要保留主表全部（如"所有用户含未下单的"）|

**典型例子**：
```sql
-- 查询用户张三的订单：用 INNER JOIN
-- 但这样"从没下过单的用户"就看不到了

-- 要看到"一单都没下的用户"：用 LEFT JOIN
```

### COALESCE：处理 NULL

```sql
COALESCE(p.name, '无商品')   -- p.name 为 NULL 时返回 '无商品'
```

> ⚠️ **聚合函数与 NULL 的陷阱**：
> `SUM(oi.quantity)` 统计"从未被购买过的商品"时返回 **NULL 而不是 0**。
> 如果用 `stock - SUM(...)` 计算，结果变成 NULL，**库存预警就失效了**。
> 必须写成 `SUM(oi.quantity) = NULL → COALESCE(SUM(...), 0)`。

### GROUP BY + HAVING

| 子句 | 作用 | 执行顺序 |
|---|---|---|
| **GROUP BY** | 分组 | 先分组 |
| **聚合函数** | 对每组计算（SUM/COUNT/AVG） | 再聚合 |
| **HAVING** | 过滤**分组后的结果** | 最后过滤 |

> 💡 **HAVING 和 WHERE 的区别**：WHERE 在分组**前**过滤行，HAVING 在分组**后**过滤组。

### 索引

**原理**：没有索引 → **全表扫描**，逐行比对；有索引 → 先查索引目录快速定位，再回表读数据。

> 💡 **索引的代价**：每次 INSERT/UPDATE/DELETE 都要同步维护索引，**增加写入开销**。

**建索引的三个原则**：

| 原则 | 说明 |
|---|---|
| 建在**高频**字段 | WHERE、JOIN、ORDER BY 用到的 |
| **不要每个字段都建** | "建得越多越好"是错的 |
| **复合索引注意列顺序** | 顺序要和查询条件一致 |

**电商实例**：

| 表 | 索引 | 对应查询 |
|---|---|---|
| orders | `(user_id, status)` 复合 | "查某用户所有已完成订单" |
| order_items | `(order_id)` | "查看某订单下所有商品" |

> ⚠️ **复合索引的方向性**：`(user_id, status)` 对 `WHERE user_id=? AND status=?` 高效，
> 但**单独按 status 查询帮助有限** —— 因为索引最左前缀是 user_id。

## ❓ 自测

1. 一对多关系的外键放在哪边？
2. 多对多为什么要用中间表？
3. 金额为什么必须用 DECIMAL？
4. products → order_items 为什么用 RESTRICT 而不是 CASCADE？
5. INNER JOIN 和 LEFT JOIN 的区别？
6. 复合索引 `(user_id, status)` 对只查 status 有效吗？

<details>
<summary>参考答案</summary>

1. 放在「多」的一方，指向「一」的一方的主键。
2. 两张表之间的外键只能记录单一方向归属，无法表达双向往返的多对多，必须用中间表拆成两个一对多。
3. 浮点数在二进制中天然存在精度误差，累加后误差会显现，导致账务不一致；DECIMAL 是精确十进制运算。
4. 为了保住历史订单完整——如果 CASCADE，删商品会连带删掉所有引用它的订单详情，用户就看不到当初买了什么。正确做法是改 status 下架而不是删除。
5. INNER JOIN 只返回两表都匹配的行；LEFT JOIN 保留左表全部行，右表无匹配时填 NULL。
6. 帮助有限，因为复合索引遵循最左前缀原则，单独用 status 无法发挥索引效果。
</details>
