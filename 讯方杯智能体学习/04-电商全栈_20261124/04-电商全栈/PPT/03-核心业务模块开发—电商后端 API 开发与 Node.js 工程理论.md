## 第 7 页

- 一、Node.js的定位——事件驱动、非阻塞I/O
- 传统同步模型中，一个请求到达后若需要查询数据库，代码会阻塞在等待数据库返回结果的这一行——在结果返回之前，CPU无法处理其他请求，则这段等待时间处于空闲状态。当并发量上升时，这种同步阻塞模型会导致大量请求排队等待，系统吞吐量受到显著限制。
- 开发者在代码层面通过回调函数、Promise或async/await来处理这些异步操作的结果，底层的事件循环则负责调度和执行顺序。
- Node.js采用非阻塞I/O模型：发出数据库查询请求后不等待结果返回，而是立即转向处理下一个请求。当数据库结果返回时，事件循环（Event Loop）会通知代码继续执行后续操作——该机制使单个进程即可同时应对大量并发请求，系统资源利用率大幅提升。

## 第 8 页

- 一、Node.js的定位——事件驱动、非阻塞I/O
- 同步阻塞模型 vs Node.js非阻塞模型：
- 对比维度 | 同步阻塞模型 | Node.js非阻塞模型
- 请求处理方式 | 串行处理，一个请求等待数据库返回期间CPU空闲 | 并行处理，等待期间可处理其他请求
- 并发能力 | 受线程/进程数量限制 | 单进程可处理大量并发连接
- 代码实现 | 同步顺序执行 | 回调/Promise/async-await处理异步结果

## 第 11 页

- 四、npm与package.json——项目依赖清单与分类
- npm init -y在项目根目录下生成package.json文件，它记录了项目名称、版本号等元信息，核心作用在于管理项目的第三方依赖包列表。换一台新机器时，只需执行npm install，npm会根据package.json中的记录自动下载所有依赖，无需手动逐个安装。
- package.json将依赖分为两类：
- dependencies存放生产环境必需的依赖包——如express（Web框架）、mysql2（数据库驱动）、dotenv（环境变量管理）——这些是服务运行时不可或缺的组件；cors（跨域中间件）仅在开发期前后端分端口时备用，生产环境由Nginx反向代理实现同源部署，天然无跨域。
- devDependencies存放仅在开发阶段使用的工具——如nodemon（文件变动自动重启服务）——这类工具在生产环境中不参与运行，无需部署到线上。

## 第 14 页

- 五、Express中间件机制——app.use()这条处理管道
- app.use()用于向Express应用注册中间件——每个请求进入应用后，会按注册顺序依次经过这些中间件函数，最后才到达匹配的路由逻辑。这条“管道”中，每个中间件在请求对象上完成特定的预处理任务，然后将控制权交给管道中的下一个函数。
- express.json()负责解析请求体中的JSON数据，将解析结果挂载到req.body上——如果它被注册在路由之后或未被注册，路由中读取req.body将返回undefined。cors()在响应头中添加跨域相关字段，仅开发期前后端分端口时备用；生产环境由Nginx反向代理实现前后端同源部署，天然无跨域，无需cors。两个中间件的注册顺序通常将express.json()放在前面，确保后续所有路由和处理函数都能通过req.body获取到已解析的请求体数据。

- 六、start与dev——两套启动脚本的分工

- 开发阶段需要频繁修改代码并验证效果。如果每次修改后都要手动按Ctrl+C停止服务、再重新执行node app.js启动，反复操作会打断开发节奏。nodemon解决了这个问题——它监控项目文件的变化，检测到保存操作后自动重启服务，开发者保存代码后即可直接验证修改结果，无需手动干预。npm run dev调用的正是这套机制。

## 第 16 页

- 七、Express应用骨架——从express()到app.listen()
- app.js是整个后端服务的入口文件，它的骨架结构在Express应用中几乎是固定的：
- const app = express()创建应用实例；
- 通过app.use()依次挂载中间件；
- 随后定义路由逻辑；
- 最后app.listen(PORT, callback)启动服务，开始监听指定端口上的请求。
- 测试路由app.get('/', (req, res) => res.json({ message: '电商后端服务运行中' }))的作用是验证Express框架本身是否正常运行。访问http://localhost:3000能看到这条JSON消息，说明骨架搭建正确，可以开始编写业务接口。如果启动时遇到Error: listen EADDRINUSE: address already in use :::3000，表示3000端口已被其他进程占用，修改PORT常量更换端口即可解决——这是骨架搭建阶段最常见的问题之一。

## 第 22 页

- 二、数据库连接池——mysql.createPool()
- mysql.createPool()创建一个连接池实例，在服务启动时预先建立一批数据库连接，请求到来时从池中获取连接使用，使用完毕后归还到池中供其他请求复用。
- createPool()接收几个关键参数：
- waitForConnections决定连接用满时新的请求是否排队等待；
- connectionLimit: 10限制池中最多同时保持10个活跃连接；
- queueLimit设置等待队列的上限，0表示不限制排队数量。

- connectionLimit: 10意味着池中最多同时保持10个活跃连接。当第11个请求到达且10个连接都在处理其他请求时，该请求会进入排队状态，等待某个连接被归还后再分配。相当于以有限的连接数量换取资源可控性的工程取舍——既能控制数据库的连接压力，又能满足正常并发需求。

## 第 25 页

- 四、db.js模块封装：——一次创建，多路由复用
- 连接池对象不应在每个路由文件中各建一份——那样等同于创建了多个独立的连接池实例，connectionLimit的限制被分散到多个池子中，失去了资源管控的实际意义。正确的做法是将createPool()封装在独立的db.js文件中，通过module.exports = pool导出一个池子实例。
- 商品路由、订单路由、购物车路由各自通过const db = require('./db')引入同一个池子对象——Node.js的模块缓存机制保证了多次require同一模块返回的是同一个实例，不会重复创建连接池。这种“数据层封装”的架构使路由文件专注处理业务逻辑，db.js负责连接管理，修改数据库地址只需更新.env和db.js一处，无需在多个路由文件中逐一查找和修改。

## 第 28 页

- 七、统一响应结构——{code, message, data}
- code表示业务状态码——0代表成功，1代表失败（注意与HTTP状态码200、404、500等属于两套独立的体系，各管各的）。
- message是给人看的提示文字，用于前端展示或调试定位。
- data承载真正的业务数据，结构随接口不同而变化。
- 代码示例框：
- {
- "code": 0,
- "message": "success",
- "data": { ... }
- }
- 统一格式的核心价值在于：前端只需编写一套判断逻辑——检查code是否为0——即可处理所有接口的响应，无需针对每个接口单独适配不同的返回结构。（注：与前端章节约定好的接口契约。）

## 第 31 页

- 九、db.query(sql, params)——参数化查询的基本写法
- 关键词搜索采用name LIKE ?的写法，SQL语句字符串中只有一个占位符?，真正的关键词内容通过params数组传入db.query(sql, params)的第二个参数。这种写法称为参数化查询——它与字符串拼接（例如"...name LIKE '%" + keyword + "%'"）有本质区别：
- 后者将用户输入的内容直接嵌入SQL语法结构中，用户输入成为SQL语句的一部分；
- 参数化查询则将用户输入作为纯数据处理，由驱动层自动进行转义，不会影响SQL语句的结构。
- 在编码时，需要先建立一个编码习惯：所有SQL查询都使用占位符加参数数组的写法，不使用字符串拼接拼接用户输入。
- ✅ 正确写法（参数化查询）：
- db.query('SELECT * FROM products WHERE name LIKE ?', [`%${keyword}%`])
- ❌ 错误写法（字符串拼接）：
- db.query(`SELECT * FROM products WHERE name LIKE '%${keyword}%'`)

- 一、SQL注入原理
- 当关键词搜索的SQL语句采用字符串拼接方式写成...name LIKE "%' + keyword + '%"时，用户输入的内容会直接嵌入SQL语法结构中。正常用户输入“手机”不会有问题，但如果输入的是精心构造的SQL片段，就可能改变整条语句原有的查询逻辑——例如输入' OR '1'='1，可能使原本的查询条件失效，返回全部数据。这不是假设的场景，早期大量Web安全事件都源于这类“将用户输入当作SQL代码执行”的漏洞。攻击者无需获取密码，仅通过构造特定的输入字符串即可绕过身份校验、访问未授权的数据。

- 二、参数化查询如何防止SQL注入

- 三、事务的ACID特性
- 原子性：要求一组操作要么全部成功，要么全部撤销，不存在“执行到一半”的中间状态。
- 订单创建接口涉及写入orders主表、写入order_items详情表、扣减products库存三个写入操作——这三步必须绑定为一个不可分割的整体。如果缺少事务保护，库存扣减成功但插入订单主表失败，数据库中将出现“库存已减但订单未生成”的数据不一致状态——原子性要防止的问题，也是订单接口必须使用事务的直接原因。

## 第 36 页

- 三、事务的ACID特性
- 事务原子性在订单创建场景中的应用：
- 操作步骤 | 成功时 | 失败时（有事务） | 失败时（无事务）
- 1. 扣减库存 | 继续下一步 | 全部撤销（rollback） | 库存已扣，无法撤回
- 2. 插入订单主表 | 继续下一步 | 全部撤销（rollback） | 订单表无记录
- 3. 插入订单详情表 | 全部提交（commit） | 全部撤销（rollback） | 详情表无记录
- 最终状态 | 三张表数据一致 | 三张表均回滚到操作前状态 | 库存与订单数据不一致

## 第 37 页

- 四、订单创建事务——三个写入操作的原子性保障
- 扣减库存使用UPDATE products SET stock = stock - ?，插入订单主表后通过orderResult.insertId获取新生成的订单ID，再循环插入订单详情表。此链路上任何一个环节出错，conn.rollback()将撤销该事务中所有已执行的操作，使数据库恢复到事务开始前的状态。全部操作成功完成后，conn.commit()将所有变更真正写入数据库。

- 开启事务 beginTransaction
- ↓
- 执行库存扣减
- UPDATE products SET stock = stock - ? WHERE id = ?
- ↓
- 插入订单主表数据
- INSERT INTO orders (...) 并获取生成的 order_id
- ↓
- 循环批量插入订单详情
- INSERT INTO order_items (...) 绑定订单ID与商品明细
- ↓
- 全部步骤无异常 → 执行 commit 提交事务，数据正式生效

## 第 39 页

- AI生成的接口代码，以下三条必须人工逐条验收：
- ① 第一条：user_id一律从token解析，禁止从URL或请求体取
- 如果user_id从URL参数或请求体中获取，攻击者只需修改这个数字就能访问他人的订单、购物车等敏感数据。正确做法是从token中解析user_id，忽略前端传的任何user_id值——即使传了也以token为准，防止水平越权。
- ② 第二条：金额一律以后端数据库价格重算，不信前端传值
- 如果接口直接使用前端传来的订单总金额，攻击者可篡改请求体中的价格，将100元的商品改成1元下单。正确做法是后端根据product_id和quantity从数据库实时查询价格并重新计算总金额，前端传的金额仅供参考，不参与实际计算。
- ③ 第三条：扣库存用条件UPDATE并判断影响行数
- 禁止先SELECT查库存再UPDATE，两步之间如果有其他请求插入，会发生超卖。正确做法是单条条件UPDATE：SET stock = stock - ? WHERE product_id = ? AND stock >= ?，然后检查影响行数——为0说明库存不足，立即回滚事务。

- 八、错误处理分层
- 订单接口中的错误返回分为两类，对应两种不同的错误性质。参数缺失、用户不存在、商品不存在、库存不足等错误返回res.status(400)——此类问题的根源在于客户端传入的请求参数不符合业务规则，调整参数后即可正常执行。另一类错误走catch (err)分支，返回res.status(500)——数据库连接中断、SQL语法错误等属于服务器端问题，客户端无法通过调整参数解决，需要服务端修复。

- 总结
- 本讲的核心认知是：后端开发本质上是在“请求—响应”之间架起一条安全、稳定、可维护的数据处理管道。Express的中间件机制让每个请求经过层层预处理后才到达路由；async/await让异步的数据库操作看起来像同步流程，消除了回调地狱；RESTful接口规范和{code, message, data}响应格式让前端和后端之间有了明确的“沟通语言”。
