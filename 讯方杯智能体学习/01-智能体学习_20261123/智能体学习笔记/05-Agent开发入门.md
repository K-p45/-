# 05 · Agent 开发入门

> **一句话**：搭一个 Agent 不难，难的是**让它稳定地做对**。这节课给的是从 0 到 1 的最短路径。

## 🎬 五步搭出可用 Agent

![[05-无代码开发五步.mp4]]

| 步骤 | 做什么 | 关键决策 |
|---|---|---|
| 1️⃣ **创建** | 选模型、写人设与系统提示词 | 用哪个模型？人设要多细？ |
| 2️⃣ **配置知识库** | 把资料喂进去 | 切分粒度多大？检索几条？ |
| 3️⃣ **集成插件** | 接上搜索、计算、数据库 | 需要哪些能力？ |
| 4️⃣ **测试调试** | 拿真实问题反复试 | 怎么构造测试集？ |
| 5️⃣ **发布分享** | 挂到网页/公众号/飞书 | 渠道和权限 |

## 1️⃣ 创建：定人设

系统提示词决定 Agent 的「出厂设置」。一个好的人设包含四块：

```text
【角色】你是 XYZ 公司的售后客服助手
【能力边界】只回答退换货相关问题，其他问题礼貌引导至对应部门
【说话风格】简洁、耐心，每次回复不超过 3 句话
【工具说明】你可以调用 query_order 查询订单状态
```

> 💡 **关键**：**「能力边界」比「能力描述」更重要**。写清楚"不做什么"，比写清楚"做什么"更能减少乱答。

## 2️⃣ 知识库：让你的 Agent 懂私事

![[05-RAG知识库.mp4]]

### 平台里长什么样

![[知识库配置.png]]

### RAG 是什么

**RAG = 检索增强生成**（Retrieval-Augmented Generation）

```text
用户提问
   ↓
① 把问题变成向量
   ↓
② 在知识库里检索最相关的几段
   ↓
③ 把「问题 + 检索结果」一起交给大模型
   ↓
④ 模型基于检索结果作答（有据可依）
```

### 为什么需要 RAG

| 问题 | RAG 怎么解决 |
|---|---|
| 模型不知道你公司的内部制度 | 把制度文档放进知识库 |
| 模型知识有截止日期 | 把最新资料放进去 |
| 模型会编造答案（幻觉） | 强制它基于检索结果回答 |

> 💡 **补充**：RAG 是**目前企业落地 AI 最主流的方式**，因为：
> - 比微调**便宜**（不用训练）
> - 资料更新**即时生效**（改文档就生效）
> - 答案**可溯源**（能指出引用的是哪一段）
>
> 代价是：**效果好不好的 80% 取决于检索质量**，而不是模型本身。

### 知识库配置的三个坑

| 坑 | 表现 | 解法 |
|---|---|---|
| **切分太碎** | 一段话被拦腰截断，语义不完整 | 按段落/标题切，保留上下文重叠 |
| **切分太大** | 检索出来的段落大部分无关，稀释信息 | 单块控制在 300-800 字 |
| **检索条数不对** | 太少漏信息，太多推高噪声和成本 | 一般 top-3 ~ top-5 起步 |

## 3️⃣ 插件：给它手脚

没有插件的 Agent **只会说，不会做**。

| 插件类型 | 例子 | 能干什么 |
|---|---|---|
| 搜索类 | 网页搜索、新闻 | 获取实时信息 |
| 计算类 | 代码执行、计算器 | 精确计算（大模型算数是弱项） |
| 数据类 | 数据库、表格 | 查真实业务数据 |
| 系统类 | 邮件、日历、工单 | 触发真实业务动作 |

> 💡 **AI 其实不擅长算数**。它做的是"概率上最像的下一个 token"，算 17×24 时可能给出错误答案。**凡是涉及精确计算，一律交给计算插件。**

---

## 4️⃣ 调试：拿真实问题反复试

### 调试不是「随便问几句」

正确的做法是建一个**小测试集**：

```text
1. 收集 20-30 条真实用户会问的问题
2. 包括：正常问题、边缘问题、恶意问题
3. 每次改完提示词/知识库，全部跑一遍
4. 记录通过率
```

### 常见故障与排查

| 症状 | 可能原因 | 先查什么 |
|---|---|---|
| 答非所问 | 提示词角色不清 | 系统提示词 |
| 乱编答案 | 没检索到 / 没强制引用 | 知识库命中率 |
| 答得太啰嗦 | 没限制长度 | 风格约束 |
| 该调工具时没调 | 工具描述不清 | 工具 description |
| 调错工具 | 多个工具描述太像 | 区分工具职责 |

> 💡 **技巧**：把**失败案例**单独存起来，每次修复都回头验证这些案例没退化。这叫**回归测试**，是 Agent 能不能上生产的分水岭。

## 🏗️ 框架选型：Coze 还是 LangChain

| 维度 | Coze（低代码） | LangChain（代码） |
|---|---|---|
| 上手难度 | ⭐ 极低 | ⭐⭐⭐ 需要编程 |
| 灵活性 | 中（平台能力边界） | ⭐⭐⭐⭐⭐ 无限 |
| 部署 | 用平台托管 | 自己部署 |
| 适合 | 快速验证、非技术团队 | 深度定制、生产系统 |

> 💡 **补充**：类似的还有 **Dify**（开源、可私有部署）、**n8n**（工作流）。
> **选型建议**：先用 Coze/Dify 把想法跑通验证价值，**确认有价值后再用代码重构**。别一上来就写代码——大部分想法活不过第一轮验证。
> 多智能体框架（AutoGen / CrewAI / LangGraph）见 [[06-多智能体系统]]。

## 🎨 三种设计模式

| 模式 | 结构 | 适合 |
|---|---|---|
| **插件驱动** | 以工具调用为核心 | 工具调用类任务（查订单、发邮件） |
| **知识库驱动** | 以检索问答为核心 | 客服、知识助手、文档问答 |
| **规则驱动** | 以流程编排为核心 | 审批、多步骤固定流程 |

> 🎯 **实际项目基本都是组合**：规则驱动做主干流程，知识库补充事实，插件负责执行。

## ⚠️ 开发注意事项

| 注意点 | 说明 |
|---|---|
| **别指望 100% 准** | Agent 是概率系统，必须设计兜底（人工接管） |
| **成本要算清楚** | 每次对话都烧 token，长上下文尤其贵 |
| **敏感操作要确认** | 转账、删除、发邮件 → 人工确认 |
| **日志要留全** | 出问题时靠日志复现 |
| **权限最小化** | 工具只给必须的那几个 |

## ❓ 自测

1. 搭一个 Agent 的五步是什么？
2. RAG 为什么比微调更常被企业采用？
3. 知识库切分为什么不能太碎也不能太大？
4. 为什么涉及计算一定要用插件而不是让大模型直接算？
5. 什么是回归测试，为什么 Agent 尤其需要？

<details>
<summary>参考答案</summary>

1. 创建（人设）→ 配置知识库 → 集成插件 → 测试调试 → 发布分享。
2. 不用训练更便宜、资料更新即时生效、答案可溯源到原文。
3. 太碎会截断语义导致检索到的片段不完整；太大会让检索结果混入大量无关内容，稀释关键信息。
4. 大模型本质是概率预测下一个 token，没有精确计算能力，容易给出看似合理但错误的结果。
5. 把历史失败案例固定成测试集，每次改动后全部重跑，确保修复没让已有能力退化。
</details>
