# 06 · 多智能体系统

> **一句话**：多智能体（Multi-Agent System）就是**把一个大任务拆给几个专家，让它们自己商量着办完**。
> 但记住：**它不是银弹，协调成本可能吃掉所有收益。**

⬅️ [[05-Agent开发入门]] ｜ [[00-总览-MOC]] ｜ [[07-生态与工具链]] ➡️

---

## 🎬 单打 vs 组队

![[06-单智能体vs多智能体.mp4]]

### 定义

> **多智能体系统由多个独立运行的智能体组成，它们通过通信和协作共同完成目标。**

每个 Agent 都是一个**自主实体**——自己有感知、能规划、会行动。

### 为什么需要多智能体

| 场景特征 | 单 Agent 的困境 | 多 Agent 的解法 |
|---|---|---|
| 任务太长 | 上下文塞爆、越做越乱 | 分段，各管一截 |
| 需要多种专长 | 一个提示词塞不下所有角色 | 一人一角 |
| 需要并行 | 只能串行，慢 | 同时开工 |
| 需要交叉验证 | 自己查自己，查不出错 | 一个写、一个审 |

---

## ⚔️ 单智能体 vs 多智能体

| 维度 | 单一智能体 | 多智能体 |
|---|---|---|
| **结构** | 单一实体，独立运行 | 多个实体，共享环境 |
| **自主性** | 高度自主，只看自己目标 | 部分自主，**受他人影响** |
| **交互性** | 只和环境交互 | 智能体之间还要交互 |
| **复杂性** | 相对简单，逻辑清晰 | **高**：要处理动态交互、不确定性、冲突 |
| **目标** | 单一目标 | 多目标，要**协调个体与群体** |

> 💡 **关键洞察**：多智能体的本质不是"更强的模型"，而是**"把复杂度从模型内部转移到模型之间"**。
> 单 Agent 是**一个大脑想清楚**，多 Agent 是**几个大脑对齐**。后者更难，因为**对齐本身就是难题**。

---

## ✨ 六大核心特点

| 特点 | 说明 | 例子 |
|---|---|---|
| **分布式处理** | 各 Agent 并行处理子任务 | 物流调度：一个管路线，一个管库存 |
| **通信与协作** | 通过消息或共享知识库交互 | 客服团队交接工单 |
| **自主性与适应性** | 各自独立决策、适应变化 | 交通系统动态调路线 |
| **模块化设计** | 便于扩展和维护 | 新增一个 Agent 就多一项功能 |
| **鲁棒性与容错** | 单个失效不影响整体 | 一个失联，其他接管 |
| **可扩展性** | 动态增加 Agent 应对复杂需求 | 项目变大就多加人手 |

> 🎯 **贯穿全场的一个词：容错**。
> 单 Agent 挂了就全完了；多 Agent 挂一个，其他的还能顶上。**这是多智能体最被低估的价值。**

## 🤝 三大协作机制

多智能体能不能跑起来，全靠这三件事：

![[06-三大协作机制.mp4]]

### 1️⃣ 通信：怎么说话

| 方式 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **消息传递** | Agent 之间直接发消息 | 实时、灵活 | 容易混乱、难追踪 |
| **共享知识库** | 都往一个地方读写 | 解耦、可追溯 | 有延迟 |

> 💡 **课程里强调的"共享知识库通信"**：所有 Agent 读同一块白板。好处是**谁写了什么一目了然**，调试特别方便——这也是为什么很多框架（如 LangGraph）默认用 state 对象传递。

### 2️⃣ 任务分配：谁来干

| 方式 | 说明 | 适合 |
|---|---|---|
| **静态分配** | 事先定好谁干什么 | 流程固定 |
| **动态分配** | 按当前负载/能力实时派活 | 任务量波动大 |

> 💡 **动态分配**听起来更高级，但**它需要一个"调度者"角色**（通常是 manager agent），这又会引入单点瓶颈。很多项目最后发现**静态 + 简单路由**反而最稳。

### 3️⃣ 冲突解决：吵架了怎么办

| 方式 | 机制 | 例子 |
|---|---|---|
| **投票** | 多数决定 | 三个 Agent 对方案投票 |
| **优先级** | 按角色权重 | 安全 Agent 有一票否决 |
| **仲裁者** | 专门有个裁判 | Manager Agent 拍板 |

> 💡 **实践中最重要的其实是"权限设计"** —— 与其事后仲裁，不如一开始就规定**谁能改什么**。安全类 Agent 有一票否决权，是最常见的做法。

## 📋 典型应用场景

| 场景 | 角色分工 |
|---|---|
| **自动化客服** | 咨询处理 Agent + 回复生成 Agent + 记录交互 Agent |
| **新闻内容生成与审核** | 写作 Agent + 事实核查 Agent + 审核 Agent |
| **智能交通管理** | 路况监测 + 信号调度 + 应急响应 |
| **会议安排** | 日程管理 + 邮件管理 + 提醒 |

> 🎯 **看这张表的共同点**：每个场景都是**「一个负责产出，一个负责把关」**。
> 这是多智能体最经典也最有效的模式——**Generator + Critic（生成+批判）**。因为**同一个模型很难审出自己的错**，换个角色来审就有效得多。

## 🛠️ 主流开发框架

| 框架 | 特点 | 适合 |
|---|---|---|
| **AutoGen**（微软） | 对话驱动，Agent 之间聊着聊着就把活干了 | 研究、快速原型 |
| **Swarm**（OpenAI） | 极简，核心就是 handoff（交接） | 轻量、教学 |
| **CrewAI** | 角色 + 任务 + 流程，概念最贴近"团队" | 业务流程 |
| **LangChain / LangGraph** | 图结构编排，可控性最强 | 生产系统 |

> 💡 **补充：LangGraph 为什么后来居上**
> AutoGen / CrewAI 是「**让 Agent 自由对话**」，灵活但**不可预测、难调试、token 烧得多**。
> LangGraph 是「**把流程画成图**」，节点和边都写死，只在需要的地方放 Agent。**牺牲一点灵活性，换来可控性和可观测性** —— 这在生产环境是决定性的。
> **建议**：原型用 AutoGen/CrewAI，上生产考虑 LangGraph。

### 开发流程

```text
1. 定义角色（每个 Agent 是谁、负责什么）
2. 定义协作流程（谁先谁后、怎么交接）
3. 实现通信（消息 or 共享状态）
4. 加冲突解决（投票 / 仲裁 / 权限）
5. 测试（重点是异常路径，不是正常路径）
6. 监控（日志、耗时、成本）
```

## ⚠️ 什么时候**不该**用多智能体

> 这一节课程没展开，但**这是最容易踩的坑**，必须补上。

| 情况 | 建议 |
|---|---|
| 任务能用单 Agent 完成 | ❌ 别拆，拆了只会更贵更慢 |
| 任务步骤少（<5 步） | ❌ 协调成本 > 收益 |
| 没有明确的分工边界 | ❌ 会互相推诿 |
| 预算/延迟敏感 | ❌ token 消耗是单 Agent 的好几倍 |

**多智能体的真实成本**：

```text
token 消耗：× 3-10 倍（每个 Agent 都要读上下文）
延迟：      串行交接会显著变慢
调试难度：  指数上升（问题可能出在任何一环）
一致性：    容易出现"各说各话"
```

> 🎯 **判断标准**：**只有当任务能清晰拆分，且拆分后的并行收益 > 协调成本时，才值得上多智能体。**

1. 多智能体最被低估的价值是什么？
2. "共享知识库"通信方式相比直接消息传递有什么优势？
3. Generator + Critic 模式为什么有效？
4. 什么情况下**不应该**用多智能体？
5. LangGraph 相比 AutoGen 的核心差异是什么？

<details>
<summary>参考答案</summary>

1. 容错性——单个 Agent 失效不会导致整个系统崩溃。
2. 解耦且可追溯，所有 Agent 在同一块"白板"上读写，谁写了什么一目了然，调试方便。
3. 同一个模型很难审出自己的错误，换个角色（不同的提示词、视角、关注点）来审，形成有效的交叉校验。
4. 任务能用单 Agent 完成、步骤少于 5 步、分工边界不清、对预算和延迟敏感时——协调成本会超过收益。
5. AutoGen 让 Agent 自由对话（灵活但不可控）；LangGraph 把流程画成图，节点边都固定（可控性、可观测性更强，适合生产）。
</details>
