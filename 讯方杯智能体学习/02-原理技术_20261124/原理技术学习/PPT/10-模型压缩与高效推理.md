## 第 6 页

- 一、显存占用问题
- 大模型的参数量直接决定了显存需求。以 FP16（半精度浮点）格式存储为例，每个参数占 2 字节，一个 70 亿参数的模型（如 LLaMA-2-7B）仅模型权重就需要约 14GB 显存。如果是 700 亿参数的模型（如 LLaMA-2-70B），则需要约 140GB——这已经超出了单张 A100-80GB 显卡的容量。

## 第 8 页

- 二、推理延迟与吞吐量
- 除了显存，推理速度也是实际部署的关键瓶颈。大模型生成文本是逐字（token）进行的，每生成一个 token 都要完成一次完整的前向计算。对于一个 700 亿参数的模型，在单张 A100 上生成一个 token 大约需要 50-100 毫秒，也就是每秒只能输出 10-20 个字。
- 假设需要为 100 个用户同时提供服务，每个用户平均请求 500 个 token 的回复，那么在不做任何优化的情况下，单卡每秒只能处理不到 1 个请求。对于在线客服、搜索助手这类场景，这样的响应速度远远不够。
- 如图：将模型拆分成多个片段，以跨多个 GPU 利用并行计算，通过并发处理请求来提高吞吐量并最大限度地减少延迟

## 第 13 页

- 一、量化
- 量化是目前最常用的模型压缩技术。通俗地说，量化就像"图片压缩"：一张 RAW 格式的照片可能有 50MB，转成 JPEG 后只有 5MB，肉眼看几乎没有差别。
- 模型量化的道理类似——把参数从 FP32（32 位浮点，每个参数占 4 字节）降低到 INT8（8 位整数，1 字节）甚至 INT4（4 位整数，0.5 字节），模型体积可以缩小 4-8 倍。
- 从高精度到低精度

![[模型压缩与高效推理/幻灯片13.PNG]]

## 第 14 页

- 一、量化
- 以 LLaMA-2-7B 为例：FP16 格式需要 14GB 显存，INT8 量化后只需 7GB，INT4 量化后仅需 3.5GB，一张普通的 RTX 3060（12GB 显存）就能运行。
- 从高精度到低精度
- 目前模型的参数绝大多数都是float32类型, 占用4个字节。
- 1MB（兆字节） = 1024KB（千字节）= 1024*1024B(字节) = 1048576B(字节)；
- 8bit（比特位）= 1Byte（字节）；
- 1024Byte（字节）= 1KB(千字节)；
- 1024KB（千字节）= 1MB（兆字节）;
- 1024MB = 1GB;
- 1024GB = 1TB;
- 比如LLaMA的参数量为7000559616，7B(70亿), 那么全精度加载这个模型参数需要的显存为：
- 7000559616 * 4 /1024/1024/1024 = 26.08G     |   4G * 7 = 28G

## 第 15 页

- 一、量化
- 量化分为两种主要方式：PTQ 与 QAT
- （Post-Training Quantization, PTQ）是在模型训练完成之后直接对权重进行量化，不需要重新训练，操作简单快速。它的优点是方便，缺点是精度损失相对较大，特别是在 4-bit 这样的极低精度下。
- 训练后量化
- （Quantization-Aware Training, QAT）则是在训练过程中就模拟量化的效果，让模型学会在低精度下也能保持好的表现。QAT 的精度损失更小，但需要额外的训练时间和计算资源。对于大多数实际部署场景，PTQ 因为操作简单、不需要 GPU 重新训练，是更常用的选择。
- 量化感知训练

## 第 17 页

- 一、量化
- GPTQ 是一种基于 PTQ 的方法，它通过逐层量化和误差补偿，在 INT4 精度下保持了较好的模型质量。GPTQ 量化后的模型可以直接在 GPU 上高效运行，是 Hugging Face 社区最流行的量化格式之一。
- AWQ（Activation-aware Weight Quantization）在量化时会考虑激活值的分布，保护那些对输出影响大的"重要权重"，因此在相同精度下比 GPTQ 的效果通常更好。
- GGUF 是 llama.cpp 项目使用的量化格式，专门为 CPU 推理优化。它支持从 Q2 到 Q8 多种精度级别，格式中包含了模型的元数据信息，用 Ollama 运行本地模型时用的就是这种格式。
- 常用量化方案：GPTQ、AWQ、GGUF

![[模型压缩与高效推理/幻灯片17.PNG]]

## 第 18 页

- 一、量化
- 量化精度越低，模型越小越快，但能力损失也越大。
- 从实际测试来看：
- INT8 量化几乎不影响模型表现，各项基准测试得分与原模型相差不到 1%；
- INT4 量化会带来 2-5% 的性能下降，但对于大部分应用场景仍然可以接受；
- INT3 和 INT2 量化则可能导致明显的质量下降，目前主要用于研究探索。
- 从实际选择来看，如果 GPU 显存充足，优先使用 INT8；如果需要在消费级显卡上运行，INT4（如 AWQ 或 GPTQ 格式）是性价比最高的方案；如果要在 CPU 上运行，选择 GGUF 的 Q4_K_M 格式。
- 精度与性能权衡

## 第 19 页

- 二、知识蒸馏
- 知识蒸馏（Knowledge Distillation）的核心思想很简单：用一个大模型（"教师"）来训练一个小模型（"学生"）。学生模型不直接从原始数据学习，而是学习教师模型的输出分布——也就是模仿老师"怎么思考"，而不只是模仿"标准答案"。这样学生模型可以获得超出其自身规模的能力。
- 蒸馏在实际中非常有效。比如 DistilBERT 只有 BERT 60% 的参数量，但保留了 97% 的性能。在大模型时代，蒸馏更是成为了缩小模型规模的核心手段。

## 第 21 页

- 三、模型剪枝
- 剪枝（Pruning）的思路是：模型中并非所有参数都同样重要，可以把不重要的参数直接去掉。这就像修剪果树——去掉多余的枝叶，树反而能结出更好的果实。
- 剪枝分为两种类型：
- 非结构化剪枝将单个权重置零，模型变得"稀疏"，但硬件支持有限；
- 结构化剪枝直接移除整个神经元或注意力头，可以直接获得加速效果。
- 目前在大模型领域，剪枝通常与量化、蒸馏组合使用，作为压缩工具箱中的一个选项。
- 结构化剪枝的可视化

![[模型压缩与高效推理/幻灯片21.PNG]]

## 第 22 页

- 四、LoRA：低秩适配
- LoRA（Low-Rank Adaptation）严格来说是一种参数高效微调技术，但它的原理与模型压缩密切相关。LoRA 的核心假设是：模型微调时权重的变化量是"低秩"的，也就是说变化量可以用两个小矩阵的乘积来近似。
- 假设原始权重矩阵是 4096×4096（约 1677 万参数），LoRA 用两个小矩阵 4096×16 和 16×4096 来表示变化量，参数量从 1677 万降到约 13 万——减少了 99%。训练时只更新这两个小矩阵，原始模型参数保持冻结不变。这样一张 RTX 4090 就能微调一个 7B 模型，而全参数微调至少需要 4 张 A100。

![[模型压缩与高效推理/幻灯片22.PNG]]

## 第 23 页

- 五、QLoRA：量化 + LoRA
- QLoRA 是在 LoRA 的基础上更进一步：先把基础模型量化到 4-bit，然后在量化模型上做 LoRA 微调。这样做的好处是双重节省——量化减少了模型本身的显存占用，LoRA 减少了需要训练的参数量。

## 第 25 页

- 一、KV-Cache
- 大模型生成文本时是逐个 token 输出的，每生成一个新 token 都需要"回顾"之前所有 token 的信息。如果每次都重新计算之前所有 token 的注意力，计算量会随着序列长度急剧增长。
- KV-Cache 的作用就像一个"笔记本"：把之前每个 token 计算过的 Key 和 Value 向量缓存起来，生成下一个 token 时直接查笔记，不用重新计算。这样每一步只需要计算新 token 的注意力，速度大幅提升。代价是需要额外的显存来存储这个缓存。对于一个 7B 模型和 2048 个 token 的上下文，KV-Cache 大约需要 2-4GB 显存。

![[模型压缩与高效推理/幻灯片25.PNG]]

## 第 26 页

- 二、FlashAttention
- FlashAttention 由斯坦福大学的 Tri Dao 团队提出，它解决的是注意力计算中的"内存墙"问题。
- 标准注意力计算需要生成一个 N×N 的注意力矩阵（N 是序列长度），对于 4096 个 token，这个矩阵就有 1677 万个元素，在 GPU 的高带宽内存（HBM）和片上缓存（SRAM）之间反复搬运数据很耗时。

![[模型压缩与高效推理/幻灯片26.PNG]]

## 第 27 页

- 三、推理框架对比
- 目前主流的大模型推理框架各有特色。vLLM 由加州大学伯克利分校开发，核心创新是 PagedAttention——像操作系统管理内存页一样管理 KV-Cache，显存利用率可达 95% 以上，是目前生产环境中吞吐量最高的开源框架。
- TensorRT-LLM 是 NVIDIA 官方推出的推理加速库，深度优化了 NVIDIA GPU 上的各项算子，适合追求极致推理速度的场景。
- Ollama 则专注于易用性，一行命令就能在本地运行各种开源模型，底层基于 llama.cpp，适合个人开发者快速上手和本地实验。

## 第 29 页

- 四、连续批处理与投机采样
- （Continuous Batching）是提升推理吞吐量的关键技术。传统批处理要等一批请求全部完成才能处理下一批，如果某个请求生成的文本很长，其他已完成的请求也要"陪等"。连续批处理允许已完成的请求随时退出、新请求随时加入，GPU 利用率可以从传统方式的 30-50% 提升到 80% 以上。
- 连续批处理
- （Speculative Decoding）则用一个小模型（"草稿模型"）快速生成多个候选 token，再用大模型一次性验证。由于大模型验证多个 token 的成本与生成单个 token 差不多，如果草稿模型猜中率高，可以获得 2-3 倍的加速效果。
- 连续批处理投机采样
