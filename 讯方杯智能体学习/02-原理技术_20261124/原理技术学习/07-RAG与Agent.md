## 🎬 一、RAG：让模型开卷考试

![[701-RAG检索增强.mp4]]

### 大模型的三个死穴

| 死穴 | 说明 |
|---|---|
| **知识过时** | 知识截止于训练数据的时间点 |
| **幻觉** | 自信地说错话 |
| **缺乏私域知识** | 没读过你公司的内部文档 |

> **一个客服场景同时踩中三条**：不知道最新产品（过时）、不懂公司政策（私域）、编造不存在的功能（幻觉）。

### RAG 的核心思路：开卷考试

```text
用户提问
   ↓
① 问题转成向量
   ↓
② 在向量数据库检索 Top-K 相关片段
   ↓
③ 把「问题 + 检索片段」组装成提示词
   ↓
④ 模型基于参考资料生成回答
```

> 💡 **"向量"是什么**：一组数字，表示一段文本的**语义**。意思相近的文本，向量也相近。
> 通过比较向量距离，就能找到与问题最相关的文档 —— **这是在比"意思"，不是比"字"**。

### RAG 和微调怎么选（重要）

| | RAG | 微调 |
|---|---|---|
| 知识更新 | **改文档就生效** | 要重新训练 |
| 成本 | **低** | 高 |
| 可溯源 | **✅ 能指出第几段** | ❌ |
| 学风格/技能 | ❌ 弱 | **✅ 强** |
| 延迟 | 多一次检索 | 更低 |

**决策口诀**：

```text
"基于特定文档回答问题"  →  RAG（客服、知识库问答）
"以特定风格/格式输出"    →  微调（行业报告生成）
两者都要                →  RAG + 微调 组合
```

> 🎯 **大多数企业级应用首选 RAG** —— 实施快、成本低、易维护。

### 适合 / 不适合 RAG

| ✅ 适合 | ❌ 不适合 |
|---|---|
| 企业知识库问答 | 要让模型"学会"某种技能 |
| 客服系统 | 知识库很少且变动不大（直接塞提示词更简单） |
| 法律助手 | |
| 医疗助手 | |

### 两个层面评估

| 层面 | 指标 |
|---|---|
| **检索质量** | 召回率（该找的都找到了吗）、精确率（找到的有多少相关） |
| **生成质量** | 忠实度（忠实于文档吗）、相关性（切题吗） |

**两个典型故障**：

| 症状 | 原因 | 解法 |
|---|---|---|
| 检索到正确文档，但回答不对 | 提示词模板有问题 | 优化提示词 |
| 检索不到相关文档 | 分块策略或 Embedding 不行 | 调分块 / 换模型 |

## 🔧 二、RAG 技术细节

### 1. 文档分块（Chunking）

**这是 RAG 最重要的预处理步骤。**

| 分块方式 | 说明 |
|---|---|
| 固定字数 | 每 500 字一块 |
| 按段落 | 保留段落完整性 |
| 按标题层级 | 保留结构 |

**大小怎么定**：

| 大小 | 问题 |
|---|---|
| 太大（2000 字） | 混入无关内容，占用上下文窗口 |
| 太小（50 字） | 语义不完整，一句话被切断 |
| **200-500 字** | **推荐范围** |

**重叠分块（Overlap）**：相邻块保留 **50-100 字**重叠，避免关键信息正好被切断在边界。

> 🎯 **一句话原则**：每个 chunk 在**语义上要完整**。

### 2. Embedding 模型

**作用**：文本 → 固定长度向量（768 或 1024 维）。

| 模型 | 特点 | 维度 |
|---|---|---|
| **BGE-large-zh** | 智源出品，**中文标杆** | 1024 |
| **M3E-base** | 开源、轻量高效 | 768 |
| text-embedding-3 | OpenAI，多语言 | —— |

### 3. 向量数据库

| 数据库 | 特点 | 适合 |
|---|---|---|
| **Chroma** | 轻量，几行代码启动 | **实验、POC** |
| **FAISS** | Meta 出品，支持 GPU | 大规模 |
| **Milvus** | 国产分布式，亿级 | **企业生产** |

### 4. 语义检索 vs 关键词检索 ⭐

| | 关键词检索（BM25） | 语义检索（向量） |
|---|---|---|
| 匹配什么 | **词** | **意思** |
| 搜"苹果手机" | 找不到只写"iPhone"的 | ✅ 能找到 |
| 优势 | 精确匹配（型号、人名） | 理解意图 |
| 劣势 | 不会联想 | 可能不准 |

**具体例子**：

```text
用户搜"屏幕有问题"
  → 关键词检索：找不到"显示器故障排查"（词不一样）
  → 语义检索：✅ 能找到（意思一样）
```

### 5. 混合检索（Hybrid Search）⭐

**做法**：**同时做两种检索**，然后融合结果。

```text
问题 ─┬→ 关键词检索（BM25）→ Top-K 列表A ┐
      └→ 语义检索（向量）  → Top-K 列表B ┤
                                          ↓
                                    RRF 融合算法
                                          ↓
                                      最终排序
```

**RRF（Reciprocal Rank Fusion）**公式：

```text
得分 = 1/(K + 排名1) + 1/(K + 排名2)

K 是常数，通常取 60
```

> 💡 **RRF 的精妙之处**：它**只看排名，不看分数**。因为两种检索的分数不可比（一个是 BM25 分，一个是余弦相似度），但**排名是可比的**。

> 🎯 实测混合检索比单独用任一种**好 5-15%**。

### 6. 余弦相似度

**衡量两个向量的夹角**：

| 值 | 含义 |
|---|---|
| 1 | 方向完全一致（极其相似） |
| 0 | 垂直（无关） |
| -1 | 方向相反 |

**例子**：
```text
A = [1, 0, 0]
B = [0.9, 0.1, 0]
cos ≈ 0.99 → 语义非常相似
```

实际中通常设**阈值 0.7**，只返回高于阈值的结果。

### 7. 提示词组装

```text
请根据以下参考资料回答用户的问题。
如果参考资料中没有相关信息，请直接说不知道。

参考资料：{检索到的文档片段}

用户问题：{用户的原始问题}
```

> 💡 **注意那句"没有相关信息就说不知道"** —— 这是负向约束（见 [[06-提示词工程]]），能显著降低幻觉。

**上下文窗口限制**：DeepSeek-V3 支持 128K，通常 **3-5 个片段（1000-2000 字）**就够回答大多数问题。

## 🚀 三、RAG 高级优化

### ① 查询改写（Query Rewriting）

**问题**：用户的原始问题表述不清晰，直接检索效果差。

| 方式 | 做法 |
|---|---|
| **同义扩展** | "大模型怎么瘦身？" → "大模型压缩 量化 蒸馏 模型瘦身" |
| **子问题分解** | 复杂问题拆成多个子问题分别检索 |
| **HyDE** | 让模型先**假设一个答案**，用答案去检索（答案的语义更接近文档） |

> 💡 **HyDE 的思路很巧妙**：问题的表述方式**通常不一样**，但**答案的表述方式一样**。所以拿"假答案"去检索，命中率更高。

### ② 重排序（Reranking）

**问题**：向量检索的 Top-K 里，排名靠前的不一定最相关。

**解法**：用**更精确的模型**对结果重新打分。

```text
向量检索 Top-20
      ↓
Reranker 模型（问题和每个片段一起输入）
      ↓
最终 Top-3 ~ Top-5
```

> 🎯 **为什么两级**：向量检索**快但粗**，Reranker **准但慢**（要对每个候选单独算）。
> 先粗筛 20 个，再精排到 3 个 —— 兼顾效率和精度。

常用 Reranker：**BGE-reranker**、Cohere Rerank。

### ③ 多路召回

从**多个通道**同时召回：全文检索 + 标题检索 + 向量检索，然后融合。

> **多路召回 + 重排序**是目前效果最好的方案，也是**生产环境的标准做法**。

### 常见问题排查表

| 问题 | 解法 |
|---|---|
| 检索不准确 | 检查分块策略，试混合检索 + 重排序 |
| 回答不忠实 | 提示词强化"只基于参考资料回答" |
| 回答太泛 | 增大 Top-K |
| 延迟太高 | 优化索引、减少 Top-K、换更快的 Embedding |

## 🎬 四、Agent：让模型会做事

![[702-Agent框架.mp4]]

### 发展历史：五个阶段

| 阶段 | 时间 | 代表 | 局限 |
|---|---|---|---|
| 早期探索 | 1950-70s | MYCIN 专家系统 | 人工定义规则、不能学习 |
| 知识库系统 | 1980s | 知识库 + 推理引擎 | 维护成本高 |
| 机器学习 | 1990-2000s | 深蓝 | 特定领域 |
| 深度学习 | 2010s | **AlphaGo** | —— |
| **LLM 驱动** | 2023- | GPT + Agent | 当前 |

### 智能体四要素

![[14-AI Agent理论/幻灯片19.PNG]]

| 能力 | 说明 |
|---|---|
| **规划** Planning | 把大任务分解为子任务，规划流程，反思执行过程 |
| **记忆** Memory | 短期（上下文，任务结束清空）+ 长期（外部知识库） |
| **工具** Tools | 计算器、搜索、代码执行器、数据库 |
| **执行** Action | 根据规划和记忆实施具体行动 |

### 记忆的分层（跟人脑对照）

| 人类记忆 | Agent 记忆 | 说明 |
|---|---|---|
| 感觉记忆（几毫秒） | **上下文记忆** | 单次会话，当前对话历史 |
| 短期/工作记忆（7±2） | **工作记忆** | 当前任务周期 |
| 长期记忆 | **语义/程序记忆** | 用户偏好、工具调用方式 |

> 💡 **这个对照很有启发**：Agent 的「上下文窗口」相当于人的工作记忆 —— **它也是有限的**。
> 所以要**外挂长期记忆**（向量数据库），就像人靠笔记和习惯一样。

### 从 CoT 到 Agent

**CoT 什么时候有效**（课程总结的三点）：

| 条件 | 说明 |
|---|---|
| **任务复杂度高** | 简单任务用 CoT 没收益 |
| **模型规模够大 + 算力足** | 小模型用 CoT 效果有限 |
| **子任务有关联性** | 有关联时 CoT 能建立"桥梁" |

> 🎯 **这是 CoT 和 Agent 的分界线**：
> CoT 是**线性**的 —— 「think step by step」，一条路往下走。
> Agent 是**循环**的 —— 规划 → 行动 → 观察 → 再规划。
> **ReAct（第6章）就是这两者的过渡形态。**

### 智能体类型（五级）

| 类型 | 机制 | 例子 |
|---|---|---|
| 简单反射 | 固定规则映射 | 温控系统 |
| 模型驱动反射 | 增加环境模型预测 | 智能交通信号灯 |
| 基于目标 | 明确目标 + 规划 | 智能导航 |
| 基于效用 | 多目标权衡 | 复杂决策 |
| 学习型 | 数据驱动优化 | AlphaGo |

<details>
<summary>参考答案</summary>

1. 知识过时、幻觉、缺乏私域知识。
2. RAG 适合"基于特定文档回答问题"（客服、知识库）；微调适合"以特定风格或格式输出"、需要模型学会某种技能。

6. 向量检索快但粗，Reranker 准但慢。先粗筛保证召回，再精排保证精度，兼顾效率和效果。
7. 规划、记忆、工具使用、执行。
