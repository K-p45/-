## 🎬 一、基础：四要素

![[601-提示词四要素.mp4]]

### 好坏对比（一眼看懂差别）

```text
❌ 差："帮我写个总结。"
     模型不知道总结什么、多长、什么风格。

✅ 好："请用 200 字以内总结以下会议记录的关键决议和待办事项，
      使用编号列表格式，重点突出每项决议的负责人和截止日期。
      [会议记录内容]"
```

### 四个基本构成

| 要素 | 作用 | 例子 |
|---|---|---|
| **角色** Role | 定身份，影响风格和专业度 | 你是一位资深合同审查律师 |
| **任务** Task | 明确要做什么 | 审查以下合同中的风险条款 |
| **格式** Format | 规定输出形式 | 以 JSON 格式输出 |
| **约束** Constraint | 设定边界 | 不超过 500 字；只基于文档回答 |

**综合示例**：

```text
角色：你是一位院校的计算机教师，擅长用通俗语言解释技术概念。
任务：请解释什么是 Transformer 架构，以及它为什么重要。
格式：分三个部分——概念解释、工作原理、实际应用，每部分 100-150 字。
约束：面向没有深度学习基础的学生，不使用数学公式，多用类比。
```

> 💡 **不一定要写全四个**。简单任务可能只需要「任务 + 格式」。但**一旦发现输出不对，先检查这四项哪个缺了**。

### Temperature 与 top_p（必考）

**它们控制的是「模型采样时的随机性」。**

| 参数 | 含义 | 设置建议 |
|---|---|---|
| **Temperature=0** | 总选概率最高的词，**输出确定** | 数据提取、代码生成 |
| **Temperature=1** | 选择更随机、有创意 | 写作、头脑风暴 |
| **top_p=0.9** | 只从累计概率前 90% 的词里采样 | 配合温度用 |

> 🎯 **实用建议**：要准确 → `T=0~0.1`；要创意 → `T=0.7~1.0`。
> **同一个提示词配不同 Temperature，效果可能天差地别** —— 调试时别忘了这个变量。

## 🎬 二、五种核心技巧

### 1️⃣ 零样本（Zero-shot）

**只给指令，不给示例。**

```text
请将以下文本分类为正面、负面或中性：
这家餐厅的菜味道还不错，但服务态度很差。
```

**依赖**：模型预训练时已经见过这个任务。

### 2️⃣ 少样本（Few-shot）

**给 2-5 个示例，让模型「照葫芦画瓢」。**

```text
示例1：文本：'这个产品太好用了！' → 情感：正面
示例2：文本：'快递太慢了，等了一周。' → 情感：负面
示例3：文本：'包装一般，东西还行。' → 情感：中性

现在分类：文本：'质量不错，就是有点贵。' → 情感：
```

> 💡 课程提到：少样本通常比零样本**好 10-20%**，尤其在**格式固定**的任务上。

### 3️⃣ 思维链 CoT ⭐

**为什么要 CoT**：
> 大模型是「预测下一个词」的机器。复杂问题直接跳到答案，中间一步错就全错。

**最著名的咒语**：

```text
"Let's think step by step" / "让我们一步步来"
```

> 💡 一项被广泛引用的研究表明，**在提示词末尾加这一句**，就能大幅提升数学和逻辑推理的表现。
> 原理：**它把"思考"变成了可以被后续步骤引用的 token** —— 相当于给模型一张草稿纸。

**例子**：

```text
问题：小明有 15 个苹果，给了小红 3 个，又买了 7 个，还剩多少？

直接问：19（可能对，但复杂题会错）
加 CoT ：
  1. 15 - 3 = 12
  2. 12 + 7 = 19
  答案：19
```

### 4️⃣ 角色扮演 + 结构化输出

**角色扮演**：

```text
❌ "请分析这份报告"
✅ "你是一位有 10 年经验的财务分析师，请从盈利能力、偿债能力、
    运营效率三个维度分析这份报告"
```

**结构化输出**：指定 JSON / 表格 / Markdown。

```text
请以如下 JSON 格式输出：
{"风险等级": "高/中/低", "风险描述": "...", "建议": "..."}
```

> 程序调用大模型时**必须**用结构化输出，否则解析器会崩。

### 5️⃣ 负向约束（这个常被忽略）

> **告诉模型「不要做什么」，有时比「做什么」更重要。**

| 类型 | 示例 |
|---|---|
| 输出长度 | 回答不超过 200 字 |
| 话题范围 | 只回答与产品相关的问题，其他礼貌拒绝 |
| 语言风格 | 使用正式商务语言，不要口语化 |
| **防幻觉** | **只基于提供的文档回答，不要编造** |

> 🎯 **最关键的一条**：`"如果你不确定，请直接说不知道"` —— 这一句能显著降低幻觉率。
> 因为模型的默认倾向是「尽力给个看起来合理的答案」，你必须明确告诉它**放弃也可以**。

### 6️⃣ 提示词模板化

实际项目不是每次手写，而是**模板 + 变量**：

```text
你是一位合同审查专员。
请审查以下 {contract_type} 合同，重点关注：{check_items}。
输出格式：{output_format}。
合同内容：{contract_text}
```

### 7️⃣ 设计检查清单

写完后过一遍这六条：

- [ ] 任务是否清晰？模型能仅凭提示词理解吗？
- [ ] 上下文够不够？背景、示例是否充分？
- [ ] 输出格式是否明确？长度、结构、风格？
- [ ] 是否设定了约束？哪些事不能做？
- [ ] 需要推理吗？要的话加上"请一步步分析"
- [ ] 换几种说法测过吗？

## 🚀 三、高级策略

![[602-高级提示与ReAct.mp4]]

### ① 自一致性（Self-Consistency）

**问题**：即使有 CoT，模型每次推理路径也可能不同，有时对有时错。

**解法**：**多次采样 + 投票**。

```text
同一个问题，跑 5 次 CoT：
  路径1 → 64
  路径2 → 64
  路径3 → 64
  路径4 → 64
  路径5 → 64
投票 → 64  ✅ 比单次更可靠
```

> 💡 **本质是用算力换准确率**。代价是 5 倍的调用成本。

### ② 思维树（Tree of Thoughts）

**CoT 的局限**：**单行道** —— 一条路走到黑，中间错了就全错。

**ToT 的做法**：像下棋一样，每步**探索多种可能**，评估每条路径，选最有希望的深入。

```text
       问题
      /  |  \
     方案A 方案B 方案C     ← 评估每个分支
      |        |
    继续     继续
      |        |
    答案
```

### ③ ReAct 框架 ⭐（通向 Agent 的关键）

**ReAct = Reasoning + Acting** —— 让模型**交替进行「思考」和「行动」**。

```text
思考：我需要查询今天的天气
行动：调用天气 API
观察：晴，28°C
思考：天气不错，适合户外活动
回答：今天适合户外活动，气温 28 度
```

> 🎯 **这是 Agent 技术的基础**。
> 传统提示词只让模型**说**，ReAct 让模型能**用工具做事**。
> 第一章说「Agent = 大模型 + 工具 + 循环」，**ReAct 就是那个循环的雏形**。详见 [[07-RAG与Agent]]。

### ④ 调试方法

| 方法 | 做法 |
|---|---|
| **逐步添加** | 从最简单开始，每次加一个元素，观察变化 |
| **对比测试** | 同一任务写 3-5 个提示词对比 |
| **失败分析** | 分析是指令不清、缺示例，还是约束不够 |
| **温度调节** | 太保守就提高，太发散就降低 |
| **日志记录** | 记录每次修改和效果，方便回溯 |

### 五、常见失败模式

| 失败模式 | 表现 | 解法 |
|---|---|---|
| **指令冲突** | 同时要求"详细"和"不超过 50 字" | 检查要求是否矛盾 |
| **信息过载** | 塞太多要求，模型遗漏 | 拆成多步 |
| **格式不示范** | 要 JSON 但没给例 | **给模板** |
| **Lost in the Middle** | 长提示词中间的内容被忽略 | **关键指令放开头或结尾** |

> 🎯 **Lost in the Middle 是个很实用的发现**：模型对提示词的**开头和结尾**更敏感，中间容易被遗忘。所以**最重要的指令要放在两头**。

### 五、未来趋势

| 趋势 | 说明 |
|---|---|
| **APO 自动提示词优化** | 让模型自己迭代搜索最优提示词 |
| **提示词压缩** | 精简表达，缩短数倍，降成本 |
| **被 Agent 部分取代** | 用户只给目标，模型自主规划 |

## ❓ 自测

1. 提示词的四个基本要素是什么？
2. Temperature=0 和 =1 分别适合什么场景？
3. CoT 为什么能提升准确率？
4. "如果你不确定就说不知道"属于哪类技巧？为什么有效？
5. 自一致性是什么原理？
6. ReAct 和普通提示词的本质区别？
7. 什么是 Lost in the Middle？

<details>
<summary>参考答案</summary>

1. 角色、任务、格式、约束。
2. T=0 输出确定稳定，适合数据提取、代码生成；T=1 更随机有创意，适合写作、头脑风暴。
3. 它把推理步骤写出来变成 token，后续计算可以引用前面的中间结论，相当于给了模型草稿纸。
4. 负向约束。因为模型默认倾向于给出看似合理的答案，明确允许它说"不知道"能显著抑制编造。
5. 对同一问题多次采样生成不同推理路径，然后投票取多数答案，用算力换可靠性。
6. ReAct 允许模型在推理过程中调用外部工具并根据结果继续推理，形成"思考-行动-观察"的循环。
7. 在长提示词中，模型对开头和结尾的内容更敏感，中间部分的指令容易被忽略。
</details>
